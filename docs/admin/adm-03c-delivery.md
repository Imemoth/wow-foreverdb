# ADM-03C: isolated CMS delivery implementation

Status: development only. ADR-020 and ADM-03A govern product policy and article identity. This document describes the new code paths; it does not approve public activation.

## File-by-file design

| File | Responsibility |
| --- | --- |
| `database/migrations/0026_editorial_delivery_control.sql` | Inactive dispatch ledger, live eligibility checks, serialized claims, acknowledgements, cancellation, compensation and audit. |
| `database/public-read/migrations/0013_cms_projection.sql` | Separate private-to-public projection, immutable revision snapshots, generation-ordered pointer, tombstones, signed receipts and bounded website RPCs. |

| `database/tests/admin_cms_delivery/`, `cms-delivery/test/`, `.github/workflows/admin-cms-delivery.yml` | Disposable PostgreSQL 16/17 negative and two-database worker checks, plus a local HTTP article/archive/RSS/sitemap journey. |

## Boundaries and lifecycle

The two new worker roles are `NOLOGIN` and cannot read authorization or projection tables directly. They can call only narrow definer functions in their respective databases. API callers and existing Collector/publisher roles receive no new access. Both private delivery control and MAC key tables start empty or disabled. A reviewed, random 32-byte key must be provisioned independently to both databases in a separate activation ceremony. The worker never reads that key. Its claim carries a two-minute HMAC authorization of intent ID, payload hash and expiry; the public database recomputes the payload hash and MAC before writing. The public database signs its committed receipt, which the private database verifies before moving `published_revision_id`. A worker with only its two call roles cannot fabricate either half.

The public transaction inserts an immutable revision snapshot, advances the article generation and writes its receipt atomically. The private transaction verifies that receipt, updates the article pointer and appends audit atomically. An expired private lease is recovered by reading the committed public receipt; if none exists and authorization remains live, the same intent can receive a new claim token. A network error after starting a public write preserves the private claim until receipt recovery can determine whether the write committed. A claim refused after revocation is cancelled and creates an ordered tombstone generation if it was already signed and may still race across databases. A revoked, expired claim is also cancelled and fenced. A newer protected intent records an audited `superseded` transition for unfinished older claims; if that newer intent is cancelled, an older signed claim still requires a tombstone. System tombstones have queue priority over ordinary intents. The worker retries unresolved failures and cancels ineligible unclaimed intents with audit. Revocation of an unclaimed unpublish without an older signed claim leaves the preceding public revision in place. A successfully acknowledged publication is durable: later expiry of its actor's grant, session or TOTP freshness does not silently unpublish it. A later authorized unpublish remains required. Failed delivery leaves the previously published revision in place until a later successful generation changes it.

Public generations must increase strictly. A signed current private intent may skip a generation that was superseded or cancelled before delivery. This lets an ordered tombstone overtake an in-flight revoked publish claim. An older signed envelope cannot replace a newer public pointer, even if its short-lived MAC has not expired. Duplicate delivery of the same intent returns its original receipt; a conflicting retry is rejected.

The public projection holds only article IDs, slugs, published revision snapshots, generations and receipts. It excludes drafts, staff, grants and approval history. The public apply function verifies the full private revision hash, removes the internal media `rights_source` and `rights_license` evidence before persistence, and stores both the source hash and a hash of the redacted public snapshot. Public readers receive only the redacted snapshot. This removes private licensing contacts and contract references from public storage and output while preserving source-to-projection integrity. Slugs are reserved in the private contract; a CMS/Git collision fails closed in the website. Collector identities, existing `/news/entry/{slug}` URLs, RSS GUIDs and observation publishing stay unchanged.

**Failure isolation (backend hotfix, migration 0028).** The worker processes each candidate intent on its own: a recoverable failure of one intent (content validation, a deterministic database error while evaluating it) is recorded with its retry state and audit event and the pass continues with the next intent. Security-critical failures (receipt mismatch, receipt after revoke), infrastructure failures (connection, authentication, resources, timeouts, any permission error) and an uncertain public outcome still stop the whole pass. See [adm-03bc-backend-hotfix.md](adm-03bc-backend-hotfix.md).

The website adapter is off unless `FDB_CMS_DISPOSABLE=1`, `FOREVERDB_DEPLOYMENT=local`, a loopback public-read PostgreSQL URL and the existing `foreverdb_web_reader` identity are present. CMS article and list reads are request bound; the RSS response uses `no-store` while enabled. A tombstone yields 404. The disposable local sitemap exposes only its CMS entries for publish/unpublish verification while the site's local `noindex` policy remains in force; the ordinary local sitemap remains empty. Production builds retain the Git and Collector behavior. This is not an activation flag for hosted environments.

## Local verification

Run `npm ci --prefix cms-delivery --ignore-scripts`, then `npm test --prefix cms-delivery`. Run `FDB_CMS_PG_IMAGE=postgres:16 bash database/tests/admin_cms_delivery/run-docker.sh` and repeat with `postgres:17`. For the two-database worker path, add `FDB_CMS_WORKER_TEST=1`; for the local HTTP journey, use `FDB_CMS_HTTP_TEST=1` with PostgreSQL 16 and installed `web` dependencies. The runner creates only disposable containers and injects a synthetic, fixed test key. Never reuse that value outside tests.

The SQL tests deny table access to API/worker roles, assert forced RLS, reject conflicting retries and stale generations, verify signed forward generations, tombstones, first publication date after a tombstone, public snapshot redaction and both revision hashes. Both SQL MAC functions are checked against a Node.js HMAC-SHA-256 vector. The worker test rejects forged delivery MACs and receipts, restores a lost private acknowledgement, verifies byte hashes, confirms in-flight revocation queues and delivers a compensating tombstone, confirms completed publication survives later grant revocation, and covers cancelled unclaimed/claimed unpublish, eligible expired-claim retry, revoked expired claims and superseded signed claims. Public row-lock and first-insert uniqueness-wait tests confirm an expiring authorization cannot write after either lock wait. The HTTP journey verifies article, archive, RSS and sitemap inclusion followed by authorized unpublish. Separate pinned GoTrue and PostgREST jobs apply 0026 with the disposable non-superuser migration operator and verify the inactive boundary; they do not replace target-configured hosted review. Existing Admin CMS, web and mandatory CI remain required on the exact PR HEAD.

## Recovery, rollback and activation gates

No automatic rollback is provided after any real CMS generation is delivered. Keep immutable receipts and revision history; recover an interrupted worker using `cms_receipt` and `cms_dispatch_recover`, then reconcile. If a public write succeeded and a private acknowledgement failed, block further delivery for that article until receipt recovery succeeds. If delivery fails or a revocation leaves a stale public article, alert an operator and run compensation; do not delete history. A rollback of the new migrations is safe only while control remains disabled, MAC keys are absent, and no delivery state, projection row or receipt exists. Once content exists, use an explicit reviewed forward recovery migration.

The two databases cannot share one transaction. A revoke after the final private recheck and before the public commit can briefly expose content. Signed claims expire after at most two minutes, and ordered tombstones limit replay, but neither removes the exposure window. The one-shot worker emits structured, non-secret timing evidence per delivered intent: article/generation, compensation flag, private intent creation, public receipt application, private acknowledgement, and worker command durations. Recovery is marked separately. A separately approved target-configured staging harness must also record the private revoke commit time and synchronized clock error, then measure revoke-to-public-tombstone and unpublish-to-absence across article, archive, RSS, sitemap and CDN. The Product Owner has not accepted a maximum window. Monitoring must alert on overdue claims, repeated retryable failures, missing receipts, failed compensation and any mismatch between private and public generations.

Before hosted activation: independent review of SQL ownership/ACL/RLS, target Supabase migration privileges and managed Auth compatibility, separate worker credentials and 32-byte MAC key provisioning/rotation, durable denial audit and privacy review, measured cross-database exposure, approved cache policy, Companion MFA session compatibility and mitigation, and explicit Owner authorization for hosted migrations, staff bootstrap, policy activation and deployment. MAC key rotation must drain or explicitly recover every outstanding claim and receipt; a one-key replacement while work is pending would make old receipts unverifiable. Compensation priority does not bound delay under worker outage, so alerting and the separately approved staging measurement remain mandatory. Do not infer those approvals from a green development PR.

## Admin UI connection plan

The approved Admin UI Preview screens remain a UX baseline. A later, separate adapter slice will replace synthetic actions with the existing authenticated ADM-03B article RPCs, then read authoritative intent and delivery states for status. It must use the ADM-01B live session, MFA freshness, scoped evaluator and revocation controls. The browser must never receive worker URLs, MACs, private database credentials or direct projection write access. An isolated browser acceptance run should cover create, edit, submit, independent approval, publish intent, delivered visibility, unpublish, denial and recovery before another Owner UI acceptance request.
