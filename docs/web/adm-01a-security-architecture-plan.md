# ADM-01A — Admin security architecture and ADM-01B contract

**Status: TECHNICAL PROPOSAL FOR REVIEW, 2026-11-10.** [ADR-020](adr-020-admin-platform-adm-00.md) is **OWNER APPROVED at product-policy level**. Every choice below is a proposed implementation contract, not an approved security design. Approval is recorded by named reviewers on this Draft PR or in a linked decision record; a green check or merge is not approval. No code, migration, account assignment, secret or environment change is authorized here.

## Boundary and evidence

The existing Account BFF seals its Supabase Auth session in an HttpOnly cookie scoped to /account and checks Auth /user. Its database RPCs check live auth.sessions. Companion and Guildbook have separate session and data boundaries. Admin must never broaden the Account cookie, expose a refresh token to browser JavaScript, use Auth user_metadata as an authority, or send staff records to the public read database. Admin roles never grant production, deployment, SQL, Cron or secret privileges. See [Account architecture](../account-v1/architecture.md#5-web-session-design), [Account security](../account-v1/security.md) and [ADR-020 permissions](adr-020-admin-platform-adm-00.md#proposed-authorization-contract).

Supabase's current [MFA guide](https://supabase.com/docs/guides/auth/auth-mfa), [TOTP guide](https://supabase.com/docs/guides/auth/auth-mfa/totp), [factor verify reference](https://supabase.com/docs/reference/javascript/auth-mfa-verify), [assurance-level reference](https://supabase.com/docs/reference/javascript/auth-mfa-getauthenticatorassurancelevel), [sessions guide](https://supabase.com/docs/guides/auth/sessions) and [JWT fields](https://supabase.com/docs/guides/auth/jwt-fields) describe TOTP challenge/verify, AAL and session_id. The repository's real-GoTrue harness pins Supabase Auth v2.197.0 (commit 4eee58f296d9698a1c2c0ae14d7a0b379c7622d3). Source inspection of that exact tag shows successful TOTP verify updates the session's totp AMR timestamp, rotates its refresh token, returns a new access token, and deletes other AAL1 sessions for the user. This is **source evidence, not a deployed-project behavior test**. A real-GoTrue integration test and a project-version/configuration check are mandatory. In particular, staff TOTP enrollment or verify may invalidate an AAL1 Companion session; product and Account/Companion owners must approve the documented reauthentication impact or a separate staff identity before activation. No global Auth setting is changed here.

## 1. Private authorization store — proposed decision

Use a dedicated, unexposed admin_private schema in the existing **private** Supabase project. No Admin tables enter the public read database. The following is the physical contract ADM-01B must map into a reviewed migration; names are proposed, and no migration is included here.

| Table | Required columns and constraints |
| --- | --- |
| policy_versions | version bigint primary key; catalog_hash; created_at; proposer_id; approver_id; activated_at. Immutable rows. |
| active_policy | singleton key constrained to 1; version foreign key; epoch bigint. Exactly one active version; activation changes version and epoch in one transaction. |
| role_permissions | (version, role, permission) primary key; foreign key to policy_versions; permission from a closed catalog; no wildcard or negative permission. |
| staff_subjects | user_id primary key referencing auth.users; status active/suspended; epoch bigint; created_at; changed_at. No role inferred from this row. |
| role_assignments | id; user_id; role; scope; starts_at; expires_at/review_due_at; status; proposal_id; approved_by; revoked_at; unique active logical assignment. Multiple roles per user. |
| direct_grants | id; user_id; permission; resource_scope; environment_scope; starts_at; expires_at; status; proposal_id; approved_by; revoked_at; reason. Check expires_at > starts_at; publish grants at most 90 days, default request 30 days. |
| staff_proposals and staff_decisions | immutable requested change, old/new values, subject, proposer, reason/ticket, expiry, created_at; independent approver, decision, time and policy version. Approved changes consume one proposal once. |
| bootstrap_control and recovery_cases | singleton consumed state and approved request digest; separate time-boxed recovery case with two operator approvals and outcome; no credentials or real owner ID in repository. |
| audit_events and audit_day_heads | event id, transaction/request id, actor/subject, action, outcome, resource/revision, policy/grant reference, UTC time, reason code, canonical payload digest, previous hash and event hash; per-day head/anchor state. |

All tables have RLS enabled and forced where the owner model permits. Revoke schema usage and table privileges from PUBLIC, anon and authenticated; default privileges must also be revoked. Do not grant direct CRUD on these tables to service_role; recognize that service_role and migration owners can bypass RLS and protect those credentials separately. SQL inspection must prove these grants, function owners and search paths. Public Data API access exists only through a small set of explicitly granted, security-reviewed RPC wrappers, following the existing Account pattern. Place helpers in admin_private; expose only individually named wrappers for entry, protected actions, proposals, approvals and revocations. Each wrapper has a fixed empty search_path, qualified object names, restricted EXECUTE (authenticated only), bounded inputs, current-JWT identity and live-session checks. Direct PostgREST callers receive exactly the same guards as the BFF. No general query, arbitrary SQL, arbitrary permission-check or service-role proxy endpoint. Security review must validate SECURITY DEFINER ownership and that no caller-controlled search_path or function overload bypass exists.

A version activation takes an exclusive lock on active_policy, validates catalog completeness/hash and independent approval, changes the singleton atomically, increments its epoch and writes an audit event. Assignments and grants reference the policy version under which they were approved; an activation revalidates or explicitly expires incompatible grants. Missing/unknown permission, missing policy, corrupt scope or unavailable store denies. Every role and grant mutation increments staff_subjects.epoch. Epochs support audit and race tests; V1 **never caches an allow decision**.

### Central permission evaluator

One database-side evaluator takes authenticated uid and session_id from validated Auth claims, named permission, resource ID/revision, environment and action class. It loads the active policy and the subject's current state, unions active roles and individual grants, then intersects resource/environment/time scope and the action-specific guards. A direct grant cannot invent a permission outside the closed catalog or exceed its approved ceiling. It returns allow/deny plus reason and references for audit; callers cannot request that it skip a guard. admin.enter is necessary for staff entry and insufficient for any action. The existing ADR-020 publishing and highlighted rules take precedence over any broader role combination. A role union never bypasses independent approval, fresh TOTP, grant ceiling or production separation. Time comparisons use database UTC clock.

## 2. No-cache revocation and protected writes — proposed decision

V1 reads authoritative private rows on **every protected decision**, including page data and each mutation. The linearization point for a database-backed mutation is its guarded transaction. Use READ COMMITTED and a single lock order: active_policy row, staff_subjects row, relevant role/grant/proposal rows, then resource/revision row. Authorization reads hold FOR SHARE locks through the write and audit insert; policy activation/revocation/suspension/expiry processing obtains conflicting FOR UPDATE locks in the same order. An auth.sessions row is checked and locked for the transaction, with uid, sid, AAL, factor and expiry validated. All protected database mutation, revision check and audit insertion occur in that one transaction. Denied attempts are logged by a separate restricted path because a denied transaction is rolled back. Lock timeout or uncertain state fails closed.

A revoke committed before the action acquires its authorization locks denies the action. If the action obtains the locks first, the revoke waits; the action commits or rolls back before the revoke commits, and the **next** decision denies. An expiry is enforced by database clock even without an expiry job. A concurrent policy activation, grant change, article revision change or last-Owner change must serialize under the same order. ADM-03 later owns atomicity of public CMS delivery; this contract does not claim a database transaction covers external effects. A later external side effect must use a durable outbox with a new authorization check or a separately reviewed compensation design. No permission cookie/JWT snapshot, polling delay, TTL cache or stale read replica is an authority.

## 3. /account to /admin session handoff — proposed decision

1. An Account POST start route requires its existing Account cookie, same-origin Origin/Referer check, CSRF token bound to that session, a live Auth /user result, and server-side admin.enter plus TOTP AAL2 verification. It generates at least 256 random bits; stores only the token hash with uid, sid, created_at, expiry (60 seconds), unused status and request binding in admin_private. Return a no-store, no-referrer response containing a same-origin POST form. The handoff token is never in a URL, redirect location, analytics event or log.
2. A same-origin Account POST completion route requires the Account cookie and CSRF again. It atomically consumes the token once with a conditional update, checks its uid and sid against the current live Account session, then rechecks admin.enter, factor and session state. Cross-account, cross-session, expired, used and parallel redeems deny. A 303 redirect to /admin occurs only after success.
3. Completion sets a separate signed/sealed, HttpOnly, Secure, SameSite=Lax cookie scoped to /admin. Its contents are the **access token only**, uid, sid, issued/expiry and a domain-separated cookie version; expiry is no later than the Auth access token expiry and 30 minutes. It contains no refresh token or role snapshot. The BFF never widens the Account cookie. An expired Admin cookie requires another Account handoff; the Account BFF alone owns refresh-token rotation. Key rotation invalidates old Admin cookies. Admin logout clears its cookie; Account local logout must make the paired Admin session inert on its next decision, with a live Auth session check and explicit local-cookie clearing where the same response can do so.
4. Each Admin request validates the cookie cryptographically, rechecks the live Auth session and private authority, and rejects a stale/suspended/revoked subject. All state-changing routes require CSRF and same-origin checks. Session state in a cookie is only a transport hint, never authority. Error, retry, concurrent refresh, clock skew, nonce replay and token leakage cases require tests. Rate limits apply to start, completion and MFA routes.

This uses no duplicate refresh token and no browser-visible Auth token. Alternatives: a root-path Account cookie increases credential exposure to unrelated routes; a server store of duplicate refresh tokens expands secret custody; a separate staff Auth identity avoids shared-session effects but adds account lifecycle burden. The selected handoff cannot be deployed until security review of cookie sealing, CSRF and Companion behavior.

## 4. MFA and 15-minute freshness — proposed decision

Staff entry requires a verified TOTP factor and live session with AAL2, not merely a JWT claim or phone-only AAL2. The Account server adds only explicit enroll, challenge, verify, list and unenroll Auth operations to its closed allowlist, each with route-specific validation, body limits, no redirects, rate limits and secret redaction. Factor management is itself critical and requires fresh TOTP when one exists; initial enrollment is handled as a controlled onboarding exception with existing account authentication, independent invitation and immediate verify. Supabase MFA must remain enabled for challenge/verify in the target project. Verification response refresh token must replace the Account sealed session atomically; failures must not leave mixed token pairs. Confirm the returned uid/sid, AAL2 and verified TOTP before continuing.

For critical actions, **fresh proof comes from GoTrue's authoritative auth.mfa_amr_claims row for the same live auth.sessions.id, authentication_method = totp, updated_at within the prior 15 minutes**. Require the session's AAL2 and associated verified TOTP factor in auth.mfa_factors; check all of this inside the protected transaction. An access-token refresh, JWT iat, Account cookie creation, or old AAL2 claim never resets freshness. Reject future timestamps outside a small reviewed clock-skew allowance; use the database clock and fail closed if Auth internals differ from the verified deployed GoTrue version. A new successful TOTP challenge/verify updates the AMR timestamp; the proof is reusable only within the 15-minute policy window in that same session. The MFA API's challenge ID and one-time verify semantics remain GoTrue's responsibility; no self-asserted BFF timestamp or caller-supplied proof can authorize an RPC. Verify factor removal, session downgrade and logout against live GoTrue data; an old JWT must not restore access. Rate-limit challenge/verify and alert on abuse.

The pinned GoTrue source shows totp AMR updated_at is refreshed on verify and AAL1 sessions may be invalidated, but the target Supabase deployment/version and project MFA configuration are **unverified**. ADM-01B must add real-GoTrue tests for initial and repeated TOTP verify, AMR timestamp, refresh-token rotation, AAL downgrade, factor unenroll, other Account/Companion sessions, logout and expired/old JWT. If the deployed Auth schema or behavior differs, stop at this gate and obtain a reviewed replacement proof design; do not infer freshness from JWT iat.

## 5. Role defaults, ceilings and staff lifecycle — proposed decision

Use the exact ADR-020 permission names and its matrix as the proposed V1 default mapping. The owner-approved publish, highlighted approval and grant duration cells are fixed; the following **non-publishing defaults require product/security sign-off**:

| Role | Default V1 non-publishing permissions |
| --- | --- |
| User | None; no admin.enter. |
| Moderator | admin.enter; moderation.case.read/decide/reverse only. |
| Editor | admin.enter; news.draft.write, news.article.preview/submit/review/classify, news.media.manage/validate. No staff/audit/ops default. |
| Administrator | admin.enter; news.article.approve_highlighted/unpublish; staff.role.propose, staff.grant.propose; audit.editorial.read, audit.staff.read. staff.role.approve, staff.grant.approve and staff.access.revoke require separate scoped grants. No publish default. |
| Owner | admin.enter; news.article.approve_highlighted/unpublish; staff.role.propose/approve, staff.grant.propose/approve, staff.access.revoke; audit.editorial.read and audit.staff.read. Owner's normal publish authority is per ADR-020. |

Editor may receive only scoped news.article.publish, news.article.unpublish, news.article.approve_highlighted or audit.editorial.read grants. Administrator may receive scoped news.article.publish, staff.role.approve, staff.grant.approve, staff.access.revoke or ops.status.read grants. Owner may receive ops.status.read only as a scoped grant. No direct grant of Owner role, admin.enter, audit.staff.read, production permission or unrestricted wildcard. A grant requires an existing eligible staff role; loss of that role invalidates dependent grants. Delegated publishing grants default to 30 days, never exceed 90 days, and renew through a fresh proposal. Other direct grants default to 30 days and cap at 90 days as a proposed ceiling; role assignments require a 90-day review, not automatic expiry, unless a shorter appointment is approved.

An Administrator proposes Moderator/Editor assignment or in-ceiling direct grants; an independent Owner approves. An Administrator with a specific approval grant may approve only Moderator/Editor and in-ceiling, non-publishing grants; publication/approval grants always require Owner approval. Administrator assignment or elevation requires two distinct active Owners to approve. Owner assignment, removal, or change of the authority ceiling requires two distinct active Owners and independent security sign-off. The proposed subject, proposer and approver must be distinct for any elevation; one person with multiple roles counts once. The first-Owner/second-Owner exceptions use the ceremony below, never a reusable general bypass. Emergency suspension/revocation is immediate by an authorized Owner (or a granted Administrator within ceiling), with a second-person retrospective review within one business day; it cannot remove the last effective Owner. Additions are two-person before effect. Every actor needs live AAL2 and fresh TOTP for proposals, decisions, grants and revocations. All proposals have explicit scope, reason, expiry, policy version and single-use decision; editing one creates a new proposal. Quarterly recertification reviews staff roles; an overdue review suspends high-risk grants until renewed.

## 6. Initial Owner, recovery and last-Owner guard — proposed decision

The initial Owner is an **existing, verified, non-anonymous Auth account selected by the product owner by exact uid outside the repository**. A security operator and a different product-owner delegate sign a time-limited, out-of-band request containing only a salted uid digest and ticket reference in durable security records. The operator confirms live TOTP AAL2 and a successful fresh challenge for that exact session. A one-time operator-only, non-Data-API bootstrap command runs in a controlled private environment; it locks bootstrap_control and staff_subjects, checks no Owner exists and exact approved target, creates one Owner assignment plus audit event, marks bootstrap consumed and commits atomically. Its credential is short-lived, restricted, separately stored, and disabled/rotated immediately after use. No public endpoint, email match, first-user promotion, reusable SQL snippet or repository secret. Two witnesses inspect the audit result and a staging rehearsal before production use. The unique first-Owner exception is recorded as such; it never makes the operator an Owner.

Before any ordinary Owner revocation, suspension, expiry, account deletion or recovery substitution, a serialized guard locks the Owner cohort and proves at least one **other** active, verified, recoverable Owner will remain. For Owner elevation after bootstrap, require two distinct active Owner approvals; if only one Owner exists, use the same two-witness security/product ceremony to add the second Owner, then retire that exception. Loss of a factor suspends affected privileged access. A second pre-enrolled verified TOTP factor, if supported and tested, may restore the same person after independent identity check; otherwise two independent security operators plus a product-owner delegate approve a short-lived recovery case. They verify identity through separately maintained channels, revoke old Auth sessions/factors, enforce new TOTP enrollment and fresh challenge, and re-evaluate Owner quorum before restoring access. Recovery never creates a standing MFA bypass or disables project MFA. Independent post-event review is required within one business day. If identity or quorum cannot be proven, **NO-GO** and escalate to an offline incident process.

Real first-Owner uid, recovery credentials, contact channels, operator identities and ticket secrets belong only in restricted operational systems. The repository records the procedure and decision evidence requirements. Security must approve the exact operator privilege, credential custody, emergency runbook and rehearsal before use.

## 7. Audit and privacy — proposed decision

A successful protected database mutation and its audit_events row commit in the **same transaction**; audit insert failure rolls back the action. Denials use a separate restricted append path with bounded rate and mandatory telemetry; if that sink is unavailable, privileged routes fail closed. Events include actor uid/sid or system identity, subject, action, result/reason, scope, immutable resource/revision, policy version, grant/proposal reference, request id and UTC timestamp. Never store Auth tokens, refresh tokens, TOTP codes/seeds, handoff values, private article bodies or sensitive recovery contacts. Audit readers are Owner/Administrator per proposed matrix, with editorial-only Editor grants; security incident access is separately controlled and logged.

Make events append-only to application roles: no UPDATE/DELETE functions, restrictive grants/RLS and a daily hash chain of canonical event payloads. A security-owned job exports signed daily head digests to an **independently administered immutable store** before the next day's close; verify continuity and alert on missing anchors. A database superuser can rewrite a local chain, so external anchors are essential. Select and configure the actual immutable store, signing key custody and outage response in security review. During anchor outage, privileged mutations fail closed after the reviewed maximum delay; do not claim a local hash alone is tamper proof. Audit consistency of external CMS effects later requires a durable outbox and its own design.

The owner-approved retention baseline is 365 days. Start at event UTC time; partition by day/month for bounded deletion, keep independently verified anchors for the same approved retention window, and purge expired events and backup copies under a documented schedule. Privacy review sets lawful basis, data minimization, subject access/redaction handling, incident hold with named authority and expiry, backup restore/purge behavior, geographic storage, readers and deletion evidence. A hold may extend an individual event only with documented approval. Recovery and bootstrap evidence may need a distinct retention schedule; no such exception is approved by this plan.

## 8. ADM-01B implementation and acceptance sequence

The following is a future implementation order **after** the approvals in section 9. No ADM-01B work is started by this PR.

1. Freeze the closed permission catalog and approved non-publishing defaults/ceilings. Add pure evaluator and proposal-state tests first; verify every ADR-020 publish/highlight rule and default deny.
2. In a disposable private database, implement the reviewed admin_private schema, RLS, default privilege revocation, narrow RPCs, policy activation and transaction/lock order. Inspect actual PostgREST exposure, function ownership and service-role handling. Run concurrent revoke/action, expiry, policy-swap and last-Owner tests with two database connections.
3. Extend the Account server's closed Auth client and build CSRF handoff plus /admin access-cookie flow. Use real GoTrue for repeated TOTP challenge/verify, live-session checks, AMR freshness, refresh rotation, factor removal, Companion continuity and replay tests. Abort if deployed Auth behavior differs.
4. Implement one protected action path at a time, each with in-transaction decision, immutable revision binding and audit. Staff proposals/approvals/revocations and bootstrap/recovery follow only after two-person and last-Owner tests. ADM-03 content storage/delivery and production privileges remain separate.
5. Rehearse incident recovery, audit anchor loss, 365-day purge/hold and rollback on staging with disposable identities. Require code/migration security review, Account/Companion/Guildbook regression suites, exact-head CI and a distinct production GO before any real assignment, schema application or activation.

Security acceptance tests must prove: ordinary/anonymous/deleted users, forged metadata and missing live sessions deny; role unions never bypass constraints; wrong scope, expired grant, unknown policy, unavailable store and revoked grant deny at the next decision; overlapping revoke/action respects the documented commit order; old JWT after logout, factor removal or AAL downgrade denies; JWT iat refresh cannot establish step-up; expired 15-minute TOTP proof denies; handoff CSRF, replay, cross-session and concurrent redemption deny; self-approval, highlighted self-approval, altered revision, classification downgrade and media swap deny; no lower role can grant Owner or remove the last Owner; direct table access by anon/authenticated denies; every successful sensitive write has an audit row or rolls back; changed audit history fails the external-anchor check. Tests must also prove public article/feed/read-model, Account, Companion and Guildbook isolation.
