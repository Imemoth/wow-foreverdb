## Priority and branch policy

**One main implementation lane at a time** is the proposed default. Scoped discovery may run alongside it. The owner explicitly allowed #174 bot work in parallel with Quest Tracker; that exception is recorded rather than treated as a new default. A confirmed outage, security incident or likely data loss may interrupt the lane with a recorded decision. New ideas enter the Idea Inbox with user problem, value, confidence, cost, risks, dependencies and displaced work. Changing priority requires the owner's dated decision.

`release` remains the protected production source. Feature, security and Dependabot work normally targets `main`; promote only a curated, reviewed release candidate or hotfix from the current `release` baseline. Never infer release readiness from a green `main` build. Both protected branches require the same ten GitHub checks; publication and live Vercel parity run only on a trusted `release` ref with their protected environments. The weekly schedule on default `main` only dispatches the release workflow and holds no Vercel secret. Publication remains manual, dry-run by default, with a separate owner GO for writes. Do not change Vercel Production Branch Tracking as part of this roadmap. See [branch governance](branch-governance-20261103.md), [release gates](release-gates.md) and [release parity](release-parity.md). Environment restrictions, reviewer policy and Vercel tracking require owner verification in Settings; repository YAML is not proof of those settings.

## Centralized Admin Platform (ADM-00–ADM-05)

**Product objective:** one authenticated `/admin` home for AzerDex staff, led by a manually operated **News CMS**. Authorized staff should create, preview, review and publish articles without a code commit or Vercel deployment. Existing Supabase Auth is the identity starting point; admin authorization is an additional server-enforced layer. Private account/operational data and the public read model remain isolated. [ADM-00 ADR-020](adr-020-admin-platform-adm-00.md) records **OWNER APPROVED** product policy, **PROPOSED** detailed defaults and **OPEN** technical/security gates; the [Admin Platform access-control specification](admin-platform-access-control.md) is its implementation-facing companion. Content storage and delivery remain **OPEN** ADM-03 choices. This roadmap authorizes no schema, privileged API, role assignment or production change.

**OWNER APPROVED system roles:** User, Moderator, Editor, Administrator and Owner, with multiple roles and controlled individual grants. An Editor has no publishing right by default; a scoped grant may let them self-publish a validated normal article. Administrator needs separate publishing authorization; Owner may publish normal content. Highlighted/high-impact content needs another authorized Administrator/Owner or specifically granted Editor to approve the unchanged revision, regardless of the publisher's Owner role. Classification cannot be downgraded to bypass approval. Publishing grants default to 30 days and last at most 90 days; staff MFA is TOTP/AAL2 with fresh authentication within 15 minutes for critical actions; audit retention has a 365-day baseline subject to privacy/security review. Group management UI is deferred beyond V1. Editorial publication does **not** grant deployment, database/public-read publication, SQL/Cron mutation, secret access or other privileged operations. Other matrix defaults and implementation design remain gated.
