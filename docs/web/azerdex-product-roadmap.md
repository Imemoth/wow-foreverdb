## Priority and branch policy

**One main implementation lane at a time** is the proposed default. Scoped discovery may run alongside it. The owner explicitly allowed #174 bot work in parallel with Quest Tracker; that exception is recorded rather than treated as a new default. A confirmed outage, security incident or likely data loss may interrupt the lane with a recorded decision. New ideas enter the Idea Inbox with user problem, value, confidence, cost, risks, dependencies and displaced work. Changing priority requires the owner's dated decision.

`release` remains the protected production source. Feature, security and Dependabot work normally targets `main`; promote only a curated, reviewed release candidate or hotfix from the current `release` baseline. Never infer release readiness from a green `main` build. Both protected branches require the same ten GitHub checks; publication and live Vercel parity run only on a trusted `release` ref with their protected environments. The weekly schedule on default `main` only dispatches the release workflow and holds no Vercel secret. Publication remains manual, dry-run by default, with a separate owner GO for writes. Do not change Vercel Production Branch Tracking as part of this roadmap. See [branch governance](branch-governance-20261103.md), [release gates](release-gates.md) and [release parity](release-parity.md). Environment restrictions, reviewer policy and Vercel tracking require owner verification in Settings; repository YAML is not proof of those settings.

## Centralized Admin Platform (ADM-00–ADM-05)

**Product objective:** one authenticated `/admin` home for AzerDex staff, led by a manually operated **News CMS**. Editors should create, preview, review and publish articles without a code commit or production deployment. The existing website authentication is the identity starting point; admin authorization is an additional server-enforced layer. Private account/operational data and the public read model remain isolated. The platform architecture, content storage and delivery mechanism are **PROPOSED** until owner acceptance; this roadmap authorizes no schema, privileged API, role assignment or production change. The [Admin Platform access-control specification](admin-platform-access-control.md) defines the proposed roles and controls.

**Proposed primary roles:** User, Moderator, Editor, Administrator and Owner. A person may hold multiple roles; narrowly scoped individual permission grants handle exceptions. Article publication is its own editorial permission. It does **not** grant production deployment, database/public-read publication, SQL or Cron mutation, secret access, or other privileged operations. Those remain under their existing release and owner gates.

| --- | --- | --- |

| **ADM-01 — RBAC and `/admin` foundation** | ADM-00; security owner reviews multiple-role RBAC, controlled direct grants and single-owner bootstrap. | Existing Auth sessions enter `/admin` only through server-side authorization; User has no staff access by default. Moderator, Editor, Administrator and Owner permissions are independently tested. Safe staff assignment, immediate revocation, MFA for staff, audit and anti-escalation tests pass; private data is never exposed through the public read model. |

Drafts/media stay private; unauthorized users cannot read or alter them. No public publish or site deploy is implied. |
| **ADM-03 — manual editorial publishing** | ADM-02; product/editorial owner approves publish and unpublish policy; security owner reviews the public-content boundary. | An authorized editor/publisher can explicitly approve and publish a reviewed revision without a code commit, Vercel deployment or database/public-read publication job. Publish events are audited and do not expose private drafts or media. |
| **ADM-04 — moderation and operations** | ADM-03; moderation owner defines queues and escalation; operations/release owners select any read-only operational surfaces separately. | Moderator can handle in-scope content reports and editorial queues with reasons, audit and appeal/reversal; cannot assign staff or deploy. None of these is an adopted architecture decision yet.
