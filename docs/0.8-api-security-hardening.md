# ForeverDB Companion — API Abuse Protection / Security Gate

Status (2026-10-09): **staged rollout; not globally locked down yet**.

This document is a factual security and deployment ledger for PR #21. It
distinguishes **isolated regression PASS**, **real production HTTPS PASS**,
**production migrations actually applied**, and **future required actions**.
An anonymous Supabase Auth login holds the Postgres `authenticated` role; an
`authenticated` GRANT is not equivalent to a paid or verified user account.
No database-only solution can guarantee immunity to volumetric DDoS.

## 1. Threats and audit observations

- Previous Companion versions used the publishable key as the bearer for
  named Search, global direct `/rest/v1/items` and `/sources` GET, stats
  and location queries. Repeated requests could be sent directly to
  PostgREST by anyone with the public key.
- The old `private` schema had `USAGE` for `anon` and
  `authenticated`; several `SECURITY DEFINER` internal helpers also
  had explicit EXECUTE grants. Raw installation tables themselves deny
  direct SELECT and have RLS. The obsolete private aggregated-all-stats
  helper was an unnecessarily powerful API surface.
- Existing `get_foreverdb_zone_catalog` correctly denied publishable-key
  only traffic, but a newly issued anonymous Auth JWT has the same
  `authenticated` role as an established Companion session. A 50-row
  page bound alone does not limit page frequency or identity creation.
- Legacy `get_foreverdb_item_locations`, `get_foreverdb_source_locations`,
  stats and zone RPCs returned aggregates under the anon role; query
  frequency and expensive join cost were unrestricted.
- SQL injection has not been demonstrated. Parameter-bound SQL already
  guards identifiers; the primary confirmed issue was excessively wide
  grants / lack of request budgets, not proven compromise.

## 2. Production changes ALREADY APPLIED

### 0008a — remove unused internal privileged entrypoints

Migration `close_unused_private_rpcs` applied on 2026-10-09
(version `20261009112031`). EXECUTE privileges were revoked from
`PUBLIC`, `anon` and `authenticated` on:

- `private.foreverdb_all_stats()`
- `private.ingest_foreverdb_snapshot_auth(jsonb)`

Post-change SQL privilege assertions **PASS** for both roles. The
supported public Search, zone browse, stats, location and authenticated
ingest entrypoints were unchanged. No existing rows were deleted.

### 0008b — nonbreaking authenticated global search

Migration `prepare_authenticated_global_search` **APPLIED to production**
on 2026-10-09. Introduces `public.get_foreverdb_search_global(text)` as
an additive, authenticated-only, server-bounded search. The simple
`Copper` query returned **one item and two sources**. `anon EXECUTE`
was false and `authenticated EXECUTE` true. Old clients remain
compatible because the legacy public table/RPC rights are not yet
revoked.

GitHub Actions

This PASS covers the tested endpoints; it does **not** prove that other
legacy anon read RPCs are closed or that the gateway resists volumetric
attacks.

## 3. 0009 strict API lockdown — STAGED, NOT PRODUCTION APPLIED

File: `database/migrations/0009_api_security_rate_limits.sql`.
Built in an isolated GitHub Postgres 16 CI instance; do **not** execute
before deploying the matching Companion binary.

- Require real Supabase `auth.uid()` and role `authenticated` for all
  Search/Stats/Locations/zone APIs.
- Remove direct `SELECT` grants for `public.items` and
  `public.sources` from `anon` and `authenticated`.
- Remove `anon` EXECUTE on all legacy read/search/ingest RPCs;
  remove `private` schema usage and helper function EXECUTE from both
  client roles.
- Use fixed 60-second per-user/global call budgets in a non-readable,
  private, atomic PostgreSQL counter table. Denials return SQLSTATE
  `PT429` → HTTP 429.
- Per-UID / global budgets: **all reads 100/300 per minute**;
  catalog **20/100 per minute**; named search **45/UID/minute**;
  details **65/UID/minute**. Ingest **5 per UID / 60 global per
  5 minutes**.
- Validate query length 2–80, disallow raw SQL LIKE wildcards for
  named searches, restrict zone offsets 0–2000 and pages 1–50,
  bound stats outputs to 500 and location outputs to 2000 rows,
  bound zone list outputs to 200.
- Limit JSON sync payload to 8 MiB, 2500 sources, 100 guild entries,
  and 15-second SQL statement timeout. Preserve current live Guildbook
  ingest implementation by moving it behind the budgeted public
  wrapper without changing its internal parser/ownership behavior.
- Public wrapper SQL is SECURITY DEFINER with an empty `search_path`;
  direct internal entrypoints remain inaccessible to the client roles.
  Migration performs privilege assertions and is atomic.
- Add sanitized errors (especially 429) in Companion so server response
  bodies, config fragments and untrusted HTML cannot appear in UI.
- Use one shared Windows-auth session for concurrent Search, Sync and
  Detail operations, avoiding a burst of new anonymous signups.
- On rapid zone/detail changes, cancel the superseded HTTP request
  and also check request-version identity before rendering.

**Isolated CI security regression: PASS**, using real PostgreSQL 16
roles/JWT claim emulation and privilege/rejection checks, including
20/minute catalog quota → 429, invalid parameters → 400, oversized
ingestion → 413, raw grants denied and expected authenticated access.
**This does not constitute a production 429 test.**
See `database/tests/api_security_roles_and_quotas.sql`,
`.github/workflows/api-security.yml` and the GitHub Actions result.

## 4. Safe single-production cutover order

The project has one production Supabase database and no established
staging project; the existing old Companion binary can still issue
publishable-key-only reads. Applying 0009 now would break its Search,
Stats and Location features. **Do not confuse isolated CI PASS with
production cutover approval.**

1. **Already complete:** deploy 0008a and 0008b, verify production
   grants and new global search (PASS).
2. Build latest `research/full-reveal-map-art-gate` Companion in the
   **Build ForeverDB Companion** workflow. Install/test it against the
   currently live additive 0008b API: numeric global `wolf`, scoped
   `Copper`, empty-zone browse, item/source detail with location and
   map, Back/Forward, Manual Sync and Guildbook. Verify that the
   new binary uses the JWT for all requests and old queries still work.
3. During an approved low-traffic maintenance window and with the
   existing snapshot/backup strategy confirmed, deploy the **single
   atomic 0009** migration via `apply_migration`; retain an
   explicit rollback contract for old client compatibility.
4. Re-run privilege checks and read-only SQL smoke. Manually launch
   `ForeverDB production HTTP authorization smoke` with
   **post_lockdown=true** in Actions for actual 401/403/200 responses
   after the ACL change. Only a few authorized HTTP calls should be
   made; do **not** load-test production for 429.
5. Test the new Companion Search/zone catalog/details/Sync again.
   Only then mark 0009 production gates PASS. If functional
   incompatibility is found, restore the specific prior ACLs under
   an approved rollback, **not** any deleted observations. Do not
   automatically grant broad privileges to anonymous clients.

The PR remains **Draft/unmerged** pending this coordination.

## 5. Platform-level protections still necessary

- **Anonymous Auth signup throttling and bot prevention:** a malicious
  party can create many identities, bypassing per-user budgets. The
  global SQL budget constrains expensive operations, but may itself
  be exhausted to deny service to honest users. Configure/check
  Supabase [Authentication → Rate Limits](https://supabase.com/docs/guides/auth/rate-limits)
  and [CAPTCHA / Turnstile](https://supabase.com/docs/guides/auth/auth-captcha)
  only after adding a compatible challenge flow to the Companion.
  Blindly enabling CAPTCHA while it still posts an empty anonymous
  signup body will break new-client authentication.
- **IP/edge pre-database throttling / WAF:** PostgreSQL quotas alone
  still accept an incoming HTTP request and some database work.
  To mitigate high-volume denial-of-service, use appropriate API
  gateway/WAF or managed edge rate limits and alerting. This requires
  provider/dashboard-level controls not available through this
  connector; it is not marked implemented.
- Enable cost usage alerts, investigate slow queries and set timeouts
  and connection limits as appropriate; run non-destructive load
  tests only in an isolated staging environment, not on the sole
  live database.
- Production `get_advisors` also reports a signed-in callable
  `SECURITY DEFINER` ingest wrapper (intended, bounded further by
  0009) and password leak-protection disabled (only relevant when
  password-based Auth is offered).
- Future true per-account data isolation/Guildbook access should be
  behind verified login and RLS/claims, not unrestricted anonymous
  Auth. The present public aggregated observations are deliberately
  separate from private installation/guild records.

Security result: **substantially hardened**, but it would be incorrect
to claim absolute non-overloadability, all API ingress behind an IP
WAF, or a full 0009 production migration PASS today.
