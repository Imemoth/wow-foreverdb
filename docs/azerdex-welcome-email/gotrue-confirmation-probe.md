# GoTrue confirmation-provenance probe (evidence)

Generated by `database/tests/welcome/probe_gotrue_confirmation.mjs` against **real GoTrue v2.197.0** (pinned, same tag as the Account suites) and disposable PostgreSQL 16.15, 2026-10-13. A temporary `AFTER INSERT OR UPDATE` trigger on `auth.users` logged every row change; each row below is one UPDATE/INSERT. Only the confirming UPDATE (`email_confirmed_at` NULL -> non-NULL) matters.

Columns shown when true: `old_ctok` = `confirmation_token` was non-empty before; `rsent` = `recovery_sent_at` is set; `ott` = `auth.one_time_tokens` rows of the user that still existed *at that moment*.

| Scenario | Result | Confirming UPDATE (non-default fields) |
|---|---|---|
| A signup -> verify(signup) | verify status 200 | new_confirmed=True, old_ctok=True, ott=confirmation_token |
| B unconfirmed signup -> recover -> verify(recovery) | recover 200, token yes, verify 200 | new_confirmed=True, old_ctok=True, rsent=True |
| C unconfirmed signup -> /otp magic link -> verify(magiclink) | otp 429, token yes, verify 403 | (no confirming UPDATE) |
| D confirmed user -> recover -> verify(recovery) | verify 200 | new_confirmed=True, old_ctok=True, ott=confirmation_token |
| E signup via OTP email (signup then verify type=email) | verify(type=email, confirmation token) 200 | new_confirmed=True, old_ctok=True, ott=confirmation_token |
| F signup confirmation token replayed as type=recovery | verify 403 | (no confirming UPDATE) |
| G confirmed user -> email change -> verify(email_change) | change 200 verify 200 newemail=g2-b22e9605@example.test | new_confirmed=True, old_ctok=True, ott=confirmation_token |
| H admin invite | invite 200, verify 200 | new_confirmed=True, invited=True |
| I admin sets email_confirm=true on unconfirmed signup | admin update 200 | new_confirmed=True, old_ctok=True, ott=confirmation_token |
| J signup, recover requested, THEN the signup link is used | verify(signup) after recover request: 200 | new_confirmed=True, old_ctok=True, old_rtok=True, new_rtok=True, rsent=True, ott=confirmation_token,recovery_token |

*Reading note:* in scenarios D and G the first row shown is the **setup** confirmation of the user (the probe signs the user up and confirms it before testing recovery / e-mail change); the later recovery and e-mail-change updates do not touch `email_confirmed_at` and therefore have no row in this table.

## Findings

1. **A plain `email_confirmed_at` NULL -> non-NULL transition is NOT sufficient.** Scenario B: a recovery link used on a still-unconfirmed signup confirms the address exactly like the signup link (and GoTrue even audits it as `user_signedup`). A password reset can therefore otherwise look like a first verification.
2. At the confirming UPDATE of a genuine signup confirmation (A, J) the user's `confirmation_token` one-time-token row still exists and `recovery_sent_at` is NULL (A); in the recovery path (B) GoTrue has already cleared every one-time token and `recovery_sent_at` is set.
3. Scenario J (recovery requested, then the *signup* link used) is a genuine signup confirmation but carries `recovery_sent_at`; migration 0015 deliberately treats it as **not** eligible (safe-side false negative).
4. Scenario I (operator sets `email_confirm` through the admin API) is row-level indistinguishable from A. It is a privileged service-role action; the candidate gate (self-service email signup after activation) still applies. Documented residual risk.
5. Invites (H) and anonymous users never become candidates (`invited_at`, `is_anonymous`). Email-change verification (G) does not touch `email_confirmed_at` of a confirmed user.
6. The rule depends on GoTrue internals. It is pinned by `database/tests/welcome/20_gotrue_provenance.test.mjs`, which must be re-run on every GoTrue upgrade and **against the hosted staging project's Auth version** (owner gate) before sending is enabled.
