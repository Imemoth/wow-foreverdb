### Modes and the recommended operating configuration

* `AZERDEX_WELCOME_MODE=html` (**code default**): version-controlled rendered HTML + text (`email.ts`) + CID attachment. Reviewed in git, locally testable, independent of any dashboard state.
* `AZERDEX_WELCOME_MODE=template`: `template: {id: "azerdex-welcome-v1", variables: {CTA_URL}}` + the same attachment (no `html`/`text`: the provider makes them exclusive with a template; the plain-text part is generated by the provider, which the G-4 message confirmed).
* **Decision: keep `html` as the code default; the recommended eventual operating configuration is `template`, set explicitly per environment.** Reasons: the default only matters when the setting is missing or mistyped, and then the safest behaviour is the path that does not depend on the state of a dashboard-hosted template (an edited, unpublished or renamed template would otherwise change or break every future mail without a code review; any value other than the exact `template` selects `html`, test TM-8). `template` matches the owner-reviewed design and was proven directly by G-4, so staging should run `template` (§ staging plan) and production should be set to `template` only after the hosted worker path passes (G-3) with that mode.
* **Switching mode is safe only with an empty retry queue.** The idempotency key comes from the database (`azerdex-welcome-v1:<user>:<epoch>`) and is identical in both modes (TM-4), so a mode switch can never create a second key for one event, but the provider answers **409** when a key is reused with a *different payload* inside 24 h (TM-5): an event that was mid-retry would then burn attempts and end in `review_required`. Before changing the setting: `select public.azerdex_welcome_stats()` must show no `retry` and no `leased` rows (or wait out 24 h); never edit the published template while events are in flight.
* A template-level problem (renamed/unpublished template, a new required variable) answers 4xx for **every** recipient. The worker parks at most **3 users per run** (consecutive permanent outcomes open the circuit; the rest are released unsent, TM-6); alert on `review_required > 0` and use `operator_requeue` after fixing the template. A verified Resend error-`name` taxonomy was not available offline, so no body parsing is done; record the real `name` values during staging if finer classification is wanted.
* Recipient: only a plain ASCII addr-spec is ever sent to the provider (no quoted local part, display name, comma, angle brackets, whitespace or non-ASCII); anything else is parked as `permanent` locally (WT-15b), so IDN users are not welcomed in V1.
* Tracking: open/click tracking is a **domain** setting; reported **OFF** by the owner (G-5, owner-attested). The payload carries no tracking tags.

## Outcomes and retries

| Provider answer | Class | Database effect |
| --- | --- | --- |
| 200/201 with a well-formed id | accepted | `sent`, provider id stored, recipient hash erased. **Accepted ≠ delivered**: no webhook is implemented, so nothing claims delivery. |
| 429 | retry (definitely not sent) | wait `max(Retry-After ≤ 3600 s, 60·2^(n-1) s)`, same key |
| timeout (headers **or body**) / transport error / 5xx / 408 / 423 / 425 / 409 / any other 2xx / malformed 2xx | **ambiguous** (may have been sent) | same key retried only inside **20 h** (Resend keeps keys 24 h); afterwards `review_required`. A 409 `invalid_idempotent_request` (payload changed within 24 h, e.g. after switching html ↔ template mode) is bounded by the 6-attempt cap and ends in review. |
| 401 / 403 | **run-level failure** (revoked key, unverified domain) | the run stops after one call; every claimed job is released with its attempt given back (`circuit_open`), **no user is parked**; log event `provider_auth_failed` must alert the operator |
| 400 / 422 / other 4xx | permanent, per recipient | `review_required`, never retried. Three consecutive permanent outcomes in one run open the circuit (rest released unsent): protects against a template-wide misconfiguration |
| expired lease (worker died) | ambiguous | as above |

Attempts are capped at 6 and 10 jobs per run (`AZERDEX_WELCOME_MAX_PER_RUN` of 0, negative or unparsable means **1**, never 10); three consecutive provider failures open a circuit for the rest of the run; a run stops starting sends after 90 s (lease 180 s, send timeout 10 s, database call timeout 10 s) and releases the rest. **There is no exactly-once guarantee**:
the database guarantees one durable event per user; the provider key de-duplicates retries inside its window; ambiguous sends beyond the window need an operator.

## Asset (G-1) — embedded, not read from disk

`supabase/functions/azerdex-welcome-worker/azerdex-logo.png` (128×128 PNG with alpha, 6,819 B, derived from the owner's `AzerDex-Icon-128.png`; provenance and hash in the function
README, pinned by `azerdex-logo.sha256`) is the reviewed source. At build time `scripts/embed-azerdex-logo.mjs` generates `logo-data.ts` (base64 + sha256) which `index.ts` imports,
so **every deploy path bundles the emblem**: Supabase cannot ship `static_files` with API-based deploys (dashboard / MCP / `--use-api`; CLI + Docker only), so a file read could have failed
silently on the hosted function. Before every run the worker validates the PNG (signature, IHDR 128×128, size cap, **every chunk CRC, IEND last, no trailing bytes**) and sends nothing otherwise
(`logo_invalid`). Tests: AS-1/AS-1b/AS-2 (asset), AS-3 (generated module current, no file read, no `static_files`), AS-5/AS-6 on a real Deno runtime with **no file-read permission**
(graph-only bundle works; a corrupted embedded emblem fails closed). Supabase's own bundler is still unverified (hosted G-7).
