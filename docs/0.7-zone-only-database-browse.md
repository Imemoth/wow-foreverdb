# Companion 0.7.2 — zone-only browse of known database entries

Status (2026-10-09): **implementation on PR #21; Windows Companion CI PASS on
code commit 71d61d3; production DB migration NOT APPLIED by this PR; live
Supabase/Windows acceptance OPEN.** Do not describe the feature as live until
the database deployment and matching Companion artifact have both passed.

## User contract

When the SEARCH text field is blank and the user chooses a specific observed
zone (e.g. Mulgore, Tirisfal Glades, Silverpine Forest), **automatically**
browse entities already present in the ForeverDB database for that exact
`map_id + zone_name` pair. The first page is 50 entries; subsequent pages
load explicitly with **Load 50 more**. The UI displays `Showing X of Y known
items and sources in <zone>`, where Y is the total count **before paging**.
The list contains items and sources (creatures by exact level, gameobjects,
fishing/fishing pools, etc.). Opening an entry uses the existing Detail,
Locations and Map behavior.

"Known in this zone" means an entry is connected to a nonzero observation in
`public.installation_location_stats` for the exact map/zone. An item additionally
needs a related `installation_item_stats.drop_count > 0`. Distinct entities
are deduplicated across installations. Item-to-zone membership is
inferred via the same installation + source + loot-kind join as the existing
zone search: when that source has observations in multiple zones, the current
schema **cannot prove exactly which zone a particular item dropped in**.
This is an honest aggregated *known source in zone* association, not an
item-drop coordinate. This deliberately does **not** claim to catalog
every NPC or gathering node that could exist in WoW but that nobody has
observed, nor items with no known zone relationship.

Named search is unchanged: text + a specific zone still calls the old
`get_foreverdb_search_in_zone` RPC; text + All zones retains the two
existing global catalog searches. **Blank text + All zones never starts an
unbounded global catalog scan** and instead prompts the user to select a
specific zone or enter a name.

Changing the zone may replace the sidebar results but must **not** reset
the open detail, breadcrumbs or Back/Forward history. An explicit new named
search still starts a new navigation session. When a result goes out of
scope, no row is highlighted; the detail persists and the explicit root
selection can be re-highlighted upon returning to a matching scope.
Stale out-of-order network responses must not overwrite the current scope.

## Backend API and security

Migration: `database/migrations/0008_zone_catalog_browse.sql` — new
`public.get_foreverdb_zone_catalog(p_map_id, p_zone_name, p_limit, p_offset)`,
delegating to `private.foreverdb_zone_catalog`. It returns
`entity_kind`, `item_id`, `source_type`, `source_id`,
`source_level`, `name`, `total_count`.
The backend caps every request to **50 rows** even if the caller provides
a larger limit. The ORDER BY includes name, kind and stable entity keys
to give deterministic offset paging on a static dataset. Each page's
COUNT(*) OVER() is an exact count at that request's database snapshot;
concurrent syncs could change counts/offsets between pages.

The read RPC uses SECURITY DEFINER **only** in the private schema with
an empty search_path, and returns aggregate public entity identities
only. Raw installations, personal identifiers, positions and per-installation
statistics are not returned. Execute privilege for the new RPC is granted
to **authenticated**, and explicitly denied to direct `anon`/PUBLIC calls.
The Companion passes its existing `SupabaseAuthService` bearer token for
this RPC; existing public name search and ingest contracts are unchanged.

**Important limitation:** Supabase anonymous sign-in issues the
`authenticated` database role. Requiring a signed-in token prevents a
publishable-key-only call, **but is not meaningful anti-scraping or private
authorization** if unrestricted anonymous sign-up remains enabled. The
50-row cap is not a server-side frequency/rate limit. Do **not** offer this
as a generally available external dataset/API without separate per-user
quotas, policy and operational safeguards. Source tables stay non-readable.

## Deployment order / live database safety

1. Review the migration and privilege implications. There is only a
   **production Supabase instance** in the current workflow; repository
   commits alone do not deploy SQL. **No production schema change has been
   executed as part of this implementation.**
2. Under an approved production change window, apply
   `0008_zone_catalog_browse.sql` after 0007 in the SQL editor or
   controlled migration process, and run the **read-only**
   `database/tests/zone_catalog_browse_smoke.sql`.
3. Independently verify that direct calls using only the publishable
   `anon` key cannot access the new RPC, while a fresh Supabase anonymous
   Auth JWT (role `authenticated`) can access one paged zone. This is
   **real HTTP transport acceptance**, not established by the SQL
   privilege smoke or portable fake HTTP tests.
4. Only then build/release the updated Companion from PR #21 and execute
   the Windows acceptance scenarios below. Without the migration,
   an empty zone browse will fail safely with a message referencing 0008;
   existing named searches continue to work.
