# Account V1 — Zero-Touch Enrollment & Registered Sync

**Status:** SPECIFICATION / DRAFT PR ONLY. No implementation, main/release merge, new live migration, public download, or live account/device enrollment is authorized by this document.
**Owner decision (2026-10-13):** One joined development milestone for registered Companion ingestion and invisible account enrollment. User should sign in once to the **ForeverDB website**, and need neither a separate Companion sign-in nor claim-code entry for a *new* installation downloaded while signed in. Downloading on home and workplace PCs must create **two distinct revocable installations** under the same registered account.

## Product contract

### A. Registered website download: zero-touch first use
1. Verified, authenticated website account requests **Download for my account** over HTTPS. It receives a regular, publicly reproducible Companion + Addon binary plus **unique per-download bootstrap metadata/ticket**, not an embedded permanent session or service key. Never build or store account-specific executables; keep the WoW addon free of secrets.
2. Bootstrap ticket is **single-use, 7 days / 168 hours valid, server-revocable**, with a securely generated unguessable secret; store server-side hash only. Every download/activation event is audited without storing the raw ticket. Rate-limit issuance and redemption, cap outstanding tickets and device count, and expire unused tickets. No URLs, logs, screenshots or analytics containing raw tickets. Use no-store private transport. Treat the ticket package as sensitive: possessing an unused bearer bootstrap is sufficient to attempt one initial binding until revoked/expired.
3. First Companion launch on a new computer generates a unique installation identity (or validates existing SavedVariables identity) AND a local per-device private key protected with Windows DPAPI; **enrollment exchanges** the ticket atomically for an installation-scoped, revocable long-lived *device* credential/binding under the ticket's original registered account. Bind the challenge to the device public key and new installation ID. Do not issue an unrestricted registered user's Supabase refresh token to any package.
4. After successful enrollment, **manual sync is available with no extra login**; auto-sync may be enabled only after dedicated owner acceptance. On the second device a fresh website download + distinct ticket creates a second installation for the same account. Once a ticket has been redeemed it cannot be replayed or exchanged again; multiple simultaneous redemptions yield exactly one winner. **Before the first successful redemption, a copied/unredeemed bearer ticket may be stolen and redeemed first by an attacker**. No client-generated key created only at redemption can distinguish that attacker from the intended installer. Record this unavoidable 7-day window in the threat model; design device attestation/issue-time binding or an exceptional website reapproval path if stronger theft resistance is required.
5. A ticket expiring while the user waits never destroys locally collected data. Recovery is a new web-signed-in **Activate this computer** action; it must not require redownloading binaries and must not silently switch the current device's owner.

### A-release. One-download, zero-manual-file handoff — **PUBLIC RELEASE BLOCKER** (owner decision 2026-10-13)

- The current PR #56 protected owner pilot deliberately downloads a separate `.fdbact` activation file. That is **pilot-only**, not an acceptable final public installation UX.
- **Required public journey:** sign in once on the ForeverDB website -> click **Download ForeverDB Companion** once -> receive **one downloadable package** -> run its installer -> Companion activates the new computer under the current account automatically (online when available). Never require a second Companion login, a separate activation-file download, a user-entered code, or manual copying between folders.
- The initial technical delivery may use one downloadable package that includes a standard installer plus enrollment bootstrap metadata, but the **release acceptance gate** is still one click/one download **and automatic installer-to-Companion ticket handoff**. A ZIP requiring the user to extract/place two files manually is not complete.
- Prefer a reproducible **single, independently signed generic installer** with a secure one-time activation handoff over generating a different unsigned executable per account. Propose and security-review the exact packaging/bootstrap mechanism (e.g., a protected download wrapper or installer handoff); make no assumptions that executable signing remains valid after modifying binary bytes. Keep the WoW Addon, static/public caches and logs free of tickets.
- Per-download ticket remains **168 hours maximum, single-use, server-revocable, unguessable, hash-only on the server**. No permanent account refresh token, device credential, or service-role secret in the installer/package. Treat an unredeemed ticket as a sensitive bearer secret: never use a public asset URL/cache/CDN log, and prevent accidental sharing/backup; consume atomically, erase the local bootstrap after successful binding, and provide secure recovery if expired without reinstalling the generic binary.
- **Second computer:** same website account, new separate one-click download, new ticket and distinct revocable registered installation. Anonymous website visitors still download the generic installer and can use anonymous collection normally; upgrading an existing anonymous installation continues to require its proven claim flow (the new-install fast path must not silently take it over).
- **Release-specific E2E gate (Windows 10 and 11):** signed-in website -> exactly one downloaded artifact -> installer -> auto-enrolled new installation -> registered manual Sync Now -> owned Private Guildbook; repeat on second PC; verify no exposed ticket, no code entry, no manual file placement, no Companion login, appropriate behavior after expiration, lost package or offline first launch, and no impact on anonymous users.
- The **#57 temporary owner-only pilot is intentionally exempt** from this packaging gate while proving the existing split-file device-enrollment/security RPC path; do not merge #57 and do not confuse pilot PASS with release readiness.

### B. Historical anonymous install
- The present anonymous Companion remains usable without registration. When the owner later creates a website account, an **already server-owned anonymous installation is NOT silently converted**. The proven one-use Claim flow + password-confirmed web redemption transfers it; once transferred, registered ingest is allowed only by an explicitly authorized installation-scoped device session. The old anonymous upload for that ID is denied. Other anonymous installs keep their existing owner and behavior.
- Detect preexisting local `session.dat`, `session.dat.bak`, saved installations and prior server owner before choosing first-run mode. If conflicting or unknown, fail closed with a clear recovery message, never overwrite original DPAPI identity or delete historical SavedVariables.
- Existing private pilot installation `2f8df8ba69345d0a14c8d56ac86d4b2e` is registered-owned after owner claim acceptance (2026-10-13). Six other installations remain anonymous; no production writes are authorized as part of this specification.

### C. Untrusted / collision / multi-account
- Installation ID alone is **not** proof of ownership: reject attempts to auto-assign server-owned, claim-pending, unknown legacy, or other-account installations. Do not first-claimer-hijack a preexisting UID. Require a device-generated proof, verified account-origin ticket and atomic unique constraints for *new* enrollment.
- One account can own many installations; one installation must never be owned by two registered accounts. Switching the signed-in website user, cloning a ticket ZIP or cloning SavedVariables must not transfer ownership.
- A device token grants **only its installation(s)' ingestion**, not account-wide Guildbook or account management; web Guildbook remains protected by registered web session, private ownership checks, and row-level policies. Revocation takes effect on ingestion and session introspection, even if cached access tokens would otherwise still be valid.

## Implementation architecture decision required before code

**Do not simply put a Supabase registered user's access/refresh token into the 7-day download.** Do not assume an anonymous per-device JWT `auth.uid()` equals the registered account UUID. The design must explicitly bridge device identity -> registered account -> authorized installation, with cryptographic proof and server-side current ownership checks. Choose and document an ADR after reviewing current PostgREST RPCs, production Supabase 0009/0012 migration, GoTrue, available Supabase Edge Function or server-only web API, and legacy anonymous identity semantics. The bridge may use a tightly scoped server-side device registry and privileged service only inside a trusted backend; **NEVER** expose a service-role/secret key to the Companion, Addon or public download. Avoid a general service-role proxy; use narrow operations with verified principal, install scope, audit and quotas.

Prefer one intentional endpoint for exchange and one for signed/device-authenticated upload (or narrow RPC equivalents). Require server-side checks for allowed JWT/device key, current revocation/session state, confirmed registered account, installation ownership, request size, data integrity, replay/race and abuse budgets; fail closed by default. Existing anonymous ingest and public read endpoints retain exactly their current permissions. RLS and SECURITY DEFINER checks must be separately audited. All migrations forward-only with an explicit rollback/recovery plan; do not change live schema without owner go/no-go.
