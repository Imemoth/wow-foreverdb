# Browser Pairing V1 — API contract

This document is normative for Browser Pairing V1. All responses are JSON, `Cache-Control: private, no-store`, strictly schema-checked
and secret-free except for the Companion's poll request body. Redirects are never followed by server clients. No handler logs request
bodies, authorization headers, pairing locators, secret verifiers or database error text.

## Common types

| Name | Contract |
| --- | --- |
| `pairingId` | lowercase canonical UUIDv4 generated by the Companion |
| `installationId` | existing Account V1 installation pattern, 16–128 characters |
| `computerName` | optional display label, control characters removed, trimmed, maximum 60 Unicode scalar values |
| `pollSecret` | `fdbp1_` plus 43 base64url characters (256 random bits) |
| `pollSecretHash` | lowercase 64-character SHA-256 hex of the exact UTF-8 poll secret |
| `deviceId` | lowercase canonical UUIDv4 generated by the Companion |
| `deviceCredentialHash` | lowercase 64-character SHA-256 hex of the complete `fdbd1_...` device secret; the credential's embedded UUID must equal `deviceId` |
| timestamp | RFC 3339 UTC timestamp |
| `intervalSeconds` | integer; initially 5, server may increase it after early polling |

Unknown fields, duplicate JSON keys, wrong casing, noncanonical UUIDs, oversized bodies and invalid UTF-8 are rejected. Error responses
use fixed public codes and never include Supabase/PostgreSQL messages.

Because only the credential hash crosses the API, embedded-device-ID equality is generated and enforced by the official Companion's
pending-record constructor. Client unit and mutation tests reject a mismatched credential before start; the server treats alternative
clients as unsupported and still binds all database use to the separately committed `deviceId` and credential hash.

## Device authentication

Start, poll and cancel are native-client routes. They require `Authorization: Bearer <anonymous Supabase access token>` and
`Content-Type: application/json`. Browser Account cookies are ignored. A request with an `Origin` header is refused unless it exactly
matches the configured site origin; no CORS response is emitted. The BFF forwards only to the one RPC assigned to the route, using the
publishable key and the same bearer token. The database is the authority for UID, anonymous status and live-session checks.

An expired access token returns 401. The Companion may refresh through its existing session manager and retry according to the poll
schedule. A route never accepts a refresh token.

## `POST /account/api/device-pair/start`

Maximum body: 2 KiB.

```json
{
  "pairingId": "8f790272-8cb2-4c5a-a57d-83c7d3d618aa",
  "pollSecretHash": "64-lowercase-hex-characters",
  "deviceId": "223e4567-e89b-42d3-a456-426614174000",
  "deviceCredentialHash": "64-lowercase-hex-characters",
  "installationId": "installation-identifier",
  "computerName": "Gaming PC"
}
```

The route calls `public.fdb_device_pair_start(uuid,text,uuid,text,text,text)`. Success:

```json
{
  "ok": true,
  "state": "pending",
  "pairingId": "8f790272-8cb2-4c5a-a57d-83c7d3d618aa",
  "verificationUri": "https://configured.example/account/device-pair?request=8f790272-8cb2-4c5a-a57d-83c7d3d618aa",
  "expiresAt": "2026-10-16T12:05:00Z",
  "intervalSeconds": 5
}
```

An identical retry by the exact initiating UID/session returns the same expiry and state. A reused ID with any changed binding or
verifier returns `pairing_conflict`. A different live pairing for the installation returns `pairing_pending`. Other fixed errors:
`feature_disabled`, `invalid_request`, `installation_conflict`, `device_bound`, `rate_limited`, `session_not_accepted`,
`temporarily_unavailable`.

## `POST /account/api/device-pair/poll`

Maximum body: 512 bytes.

```json
{
  "pairingId": "8f790272-8cb2-4c5a-a57d-83c7d3d618aa",
  "pollSecret": "fdbp1_<43 base64url characters>"
}
```

The route calls `public.fdb_device_pair_poll(uuid,text)`. The caller UID and session ID must exactly match start. Responses:

```json
{ "ok": true, "state": "pending", "intervalSeconds": 5, "expiresAt": "2026-10-16T12:05:00Z" }
{ "ok": true, "state": "approved", "intervalSeconds": 5, "expiresAt": "2026-10-16T12:05:00Z" }
{ "ok": true, "state": "connected", "deviceId": "223e4567-e89b-42d3-a456-426614174000" }
{ "ok": true, "state": "expired" }
{ "ok": true, "state": "denied" }
{ "ok": true, "state": "revoked" }
```

An approved poll attempts atomic redemption. A repeated poll after connection returns the same `deviceId` without a write. Polling
before `next_poll_at` returns HTTP 429 with `Retry-After` and `{ "ok": false, "error": "slow_down", "intervalSeconds": <new> }`;
the stored interval increases by five seconds to a maximum of 30. Invalid secrets, locators or actor bindings share the response
`pairing_not_available` so the endpoint is not an oracle. Such invalid requests may consume only principal/global abuse budgets; they
must not update the pairing row, pairing budget, `next_poll_at` or interval.

Redemption failures are classified consistently. `device_limit` and `account_limit` leave the row `APPROVED` and may be retried until
expiry after the owner fixes the limit. Lock timeout, server unavailability and rate limiting are also retryable and write no pairing
state. Approval-session revocation, account deletion/ban/unconfirmation, ownership conflict, failed predecessor binding, and proposed
device ID collision atomically change the row to `DENIED` with an internal fixed reason and no ownership/device write.
When the feature gate is off, poll returns `feature_disabled` without changing state.

## `POST /account/api/device-pair/cancel`

Uses the poll body and calls `public.fdb_device_pair_cancel(uuid,text)`. The exact initiating UID/session and secret are required.
`PENDING` or `APPROVED` changes to `DENIED` with an internal `companion_canceled` reason. `CONNECTED`, `DENIED`, `EXPIRED` and
`REVOKED` are returned unchanged. Cancel never revokes a connected device; that is the existing authenticated account action.

## `GET /account/device-pair?request=<pairingId>`

This is the only URL carrying a locator. It performs no pairing mutation. It validates the canonical UUID, creates a five-minute or
shorter HMAC-signed `__Secure-fdb_pair` HttpOnly cookie containing the ID, fresh browser nonce and expiry, and issues a 303 redirect to
`/account/device-pair`. Hosted cookies are `Secure`, `SameSite=Lax`, `Path=/account`; local loopback follows the existing development
cookie policy. Responses set `Referrer-Policy: no-referrer` and no-store headers.

An existing pairing cookie is replaced only by this explicit GET. Approve/deny include the rendered pairing ID in the JSON body and
require it to match the signed cookie, preventing another tab from silently changing the action target.

## `GET /account/device-pair`

Requires the signed pairing cookie. Without a registered Account session it redirects to `/account/login?next=/account/device-pair`;
`safeNext` admits that exact path and no descendants or query. With a session, the server calls
`public.fdb_account_device_pair_preview(uuid)` using the user's access token.

Pending/approved previews expose only:

```json
{
  "state": "pending",
  "computerName": "Gaming PC",
  "installationSuffix": "…174000",
  "requestedAt": "2026-10-16T12:00:00Z",
  "expiresAt": "2026-10-16T12:05:00Z",
  "canApprove": true
}
```

The page separately renders the verified Account email from the existing `/me` contract. It never exposes anonymous UID/session,
device ID, full installation ID, hashes, secrets or the account which won a concurrent approval. A conflict returns a generic
`cannot_connect_to_this_account` presentation.

## `POST /account/api/device-pair/approve`

Requires the existing live registered session, exact Origin/`Sec-Fetch-Site`, JSON content type, session-bound CSRF header/cookie,
signed pairing cookie, and an opaque `x-fdb-pairing-page` proof minted into the rendered page. That HMAC binds the signed locator
payload (including its nonce and expiry), the verified Account UID and the exact GoTrue session ID. It contains no identifier and is
not an authenticator by itself; the live session, signed locator and CSRF proof remain mandatory. A first click after another tab
switches accounts therefore fails before any RPC, even if that click obtains a fresh CSRF token for the new account. The request body
remains exactly `{ "pairingId": "<uuid>" }`. It calls
`public.fdb_account_device_pair_approve(uuid)`. The current `auth.uid()` and JWT `session_id` are the only approval identities; the
database stores both and redemption requires that exact registered session to remain live.

Success changes only pending to approved:

```json
{ "ok": true, "state": "approved" }
```

Fixed failures: `expired`, `already_decided`, `cannot_connect_to_this_account`, `rate_limited`, `unauthenticated`, `forbidden`,
`temporarily_unavailable`. Unknown mutation outcomes are reported as `unknown_outcome`; the UI reloads preview rather than retrying
blindly. The pairing cookie is cleared after a confirmed terminal/approved response.

## `POST /account/api/device-pair/deny`

Uses the same browser protections and exact body as approve, calling `public.fdb_account_device_pair_deny(uuid)`. It changes pending to
denied. Approved can be denied only by the same `approved_account_uid` before redemption; other accounts get `already_decided`.
Connected is immutable through this route. The cookie is cleared after a confirmed response.

## Rate budgets

The BFF applies the existing deployment-appropriate IP limiter without using a secret as a key. SQL applies authoritative budgets:

| Operation | Per principal | Per pairing | Global |
| --- | ---: | ---: | ---: |
| start | 5 / 5 min per anonymous UID | 3 / 5 min per installation hash | 120 / 5 min |
| preview | 30 / 5 min per registered UID | 60 / 5 min | 600 / 5 min |
| approve + deny | 10 / 5 min per registered UID | 5 total / 5 min | 120 / 5 min |
| poll | interval-enforced plus 90 / 5 min per anonymous UID | interval state | 3,000 / 5 min |
| cancel | 10 / 5 min per anonymous UID | 5 / 5 min | 120 / 5 min |

Exact values may only change through reviewed code and matching contract tests.

All RPCs use the global database lock order in the state-machine specification. Principal and global abuse budgets are charged before
an untrusted locator is treated as authoritative. Pairing-specific throttles and poll schedule changes occur only after the pairing
actor and secret have been verified under lock.
