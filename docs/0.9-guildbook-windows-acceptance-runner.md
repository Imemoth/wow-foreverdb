# Guildbook Local-Only V1 – Windows acceptance launcher

Source baseline: PR #112, commit `b47606061e21173ac091916e100cd51988d7ba90`.
This PR only adds a test harness. No migration, deployment, production upload,
installer, existing branch changes or automatic merge.


## Resumable synthetic GUI acceptance (PR #118 follow-up)

**Scenario:** The synthetic offline test has stopped at
`offline_gate_a = BLOCKED` because the operator controls the Windows machine
remotely. Do **not** disconnect its internet connection via remote desktop:
the connection would be lost. This is a normal **defer**, not a Guildbook
functional FAIL.

**The already-generated phase-A fixture can be reused**; do not regenerate it,
delete any historical Companion files, or replay the old JSON report as trusted
proof. The previous report is not cryptographically bound to the fixture.
Instead, start a new DPAPI CurrentUser-sealed checkpoint by manually confirming
the *current* Account A session and synthetic WoW settings. The existing
fixture and its phase-A data are preserved.

Update/download these two **additional** files from this PR branch into
`C:\ForeverDB-Test\acceptance` (keep the pre-existing
`GuildbookAcceptance.Core.psm1` and `GuildbookSynthetic.Core.psm1`):

- `GuildbookResume.Core.psm1`
- `Invoke-GuildbookSyntheticResume.ps1`

**Prepare now while remote (safe: NO offline work, no upload):**

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\ForeverDB-Test\acceptance\Invoke-GuildbookSyntheticResume.ps1' -Action Prepare -DeferOffline
```

The script automatically selects the fixture only if there is exactly one
eligible phase-A fixture. Otherwise specify its **fixture directory** (parent
of `wow`, containing `.synthetic-fixture.json`) explicitly:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\ForeverDB-Test\acceptance\Invoke-GuildbookSyntheticResume.ps1' -Action Prepare -FixtureRoot 'C:\ForeverDB-Test\synthetic-fixtures\synthetic-<YOUR_ID>' -DeferOffline
```

`Prepare` checks the pinned Companion ZIP and extracted build, DPAPI,
fixture phase-A digest, the **empty** active Guildbook store, selected WoW root,
and disabled Auto Sync; then asks for one confirmation that Account A is
currently signed in and server verified. Type `P` only if observed.
It creates `.guildbook-acceptance-resume.dpapi` under the fixture root
using Windows DPAPI CurrentUser, without putting account names, tokens,
encrypted Guildbook data, Windows SID or file hashes in the **JSON report**.
The encrypted checkpoint itself stores hashes, the local path and SID; keep it
private and do not attach it to a GitHub issue.

**Safe status check at any time:**

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\ForeverDB-Test\acceptance\Invoke-GuildbookSyntheticResume.ps1' -Action Status
```

**Resume later, physically at the Windows PC:**

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\ForeverDB-Test\acceptance\Invoke-GuildbookSyntheticResume.ps1' -Action Resume
```

While still remote, append `-DeferOffline` to Resume to avoid any
network-disconnection request; the offline step stays BLOCKED and the
checkpoint is retained. Without that switch, the launcher asks you to confirm
that you are **physically present**, then checks active IPv4/IPv6 default
routes. The operator must still disconnect *all* internet paths before pressing
`Sync now`; route inspection is not a formal proof of isolation.
The script **does not** disable adapters, make API requests, launch the
Companion, or click the upload button.

After every accepted UI milestone, the progress stage, redacted evidence and
current store fingerprint are atomically persisted to a DPAPI-protected
checkpoint. A later Resume revalidates the same Windows machine and SID,
pinned package/executable, settings, fixture manifest/phase, and encrypted
local snapshots. A mismatched or damaged checkpoint yields BLOCKED, never an
automatic PASS. Each offline safety gate is **rechecked**, and the current
account/UI state is manually reconfirmed as needed.

**No previous acceptance is imported blindly.** Changing the machine,
Windows identity, Companion build, synthetic fixture or user data invalidates
continuation. Create an entirely new fixture rather than bypass checks.
If a legitimate operation occurs between a UI click and its checkpoint write,
the runner may block conservatively; it does not delete or overwrite data
to recover. For complete results, a true WoW runtime capture and separately
authorized public sync/no-Guildbook-RPC telemetry still remain outstanding.

If you intentionally backed up the original
`%LOCALAPPDATA%\ForeverDB` folder and are now using a fresh,
empty Companion profile, the resumable fixture can be used in the **same**
Windows user. This is an explicit operator choice, not an automatic cleanup
feature: the runner never resets historical data or changes other WoW profiles.

### Synthetic resume self-test

## Game-free synthetic offline GUI exercise (before November 4)

This **separate** mode does not use the real WoW client or old Public Beta files.
It generates a unique synthetic installation and a schema-9 `ForeverDB.lua`
with fresh H/G/C/P records. Use Windows Sandbox or a dedicated Windows test user,
**not a historical profile**; the Companion itself persists its Settings,
account credentials and new encrypted Guildbook snapshots in that user's
`%LOCALAPPDATA%`. The fixture generator writes ONLY to a new folder under
`C:\ForeverDB-Test\synthetic-fixtures` and refuses to overwrite any
non-owned file. It never reads production SavedVariables or private tokens.

Download these FOUR files from PR #118's
`scripts/guildbook-acceptance` folder into
`C:\ForeverDB-Test\acceptance`:

- `GuildbookAcceptance.Core.psm1`
- `GuildbookSynthetic.Core.psm1`
- `Invoke-GuildbookSyntheticOffline.ps1`
- `Invoke-GuildbookAcceptance.ps1` (for later real acceptance)

Run from ordinary **Windows PowerShell 5.1**:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\ForeverDB-Test\acceptance\Invoke-GuildbookSyntheticOffline.ps1' -ArtifactZip 'C:\ForeverDB-Test\ForeverDB-Companion-win-x64.zip' -CompanionDirectory 'C:\ForeverDB-Test'
```

The launcher checks the pinned 0.9.0 artifact and Windows DPAPI, rejects a
profile that already contains Guildbook snapshot files, and creates a
disposable synthetic WoW root. It prints the root. In the Companion, set
**Settings > WoW root** to this printed root; turn **Auto Sync OFF**, save,
confirm the synthetic installation on Account, and authenticate test Account A
**online**. The fixture begins with a header only: do not use Sync now yet.

Once the script generates a fresh synthetic A capture, **disconnect ALL internet
routes**, including Ethernet/VPN/tethering. The launcher checks the active
default routes and does NOT authorize manual Sync now unless none are connected.
Under this offline guard, click **Status > Sync now** manually. The Companion
first saves the private Guildbook locally using CurrentUser DPAPI; its
attempted public request will fail offline. The public sync **error** is
expected and must not be counted as successful sync. The private Guildbook A
should be visible. Never click Sync now while online in this exercise.

Reconnect only for account sign-out and sign-in to test Account B, with
Auto Sync still off. While offline, reprocess the still-unchanged A fixture
and confirm it cannot appear under B; the script checks that the local
store did not change. It then creates fresh synthetic Guildbook B data
with the same installation ID and a newer capture timestamp, and prompts
one more offline Sync now. The launcher verifies a separate hashed B
account namespace and preservation of the A encrypted snapshot.
Return online to A, then test startup restoration both online and offline
without invoking Sync now.

The script **never** sends traffic, starts the client, disables adapters,
presses UI controls, changes a real WoW client or touches stored private
Guildbook contents. Because the production Companion's Sync now can upload
public observations while online, it is explicitly forbidden when connected
to any network in this synthetic exercise. No connectivity test can prove
the absolute absence of alternate network routes, so this is a conservative
routing gate plus a mandatory human observation, not a sandbox guarantee.

Results are reported in the same redacted JSON format with
`mode = SYNTHETIC_OFFLINE_GUI_EXERCISE`.
The **complete** acceptance result remains `BLOCKED` even when all
synthetic UI tests pass: a genuine addon capture, separately authorized
public sync, and runtime proof of no Guildbook RPC cannot be inferred from
an offline fixture. Existing CI source-level no-RPC coverage is independent
of this missing runtime observation. Exit code 2 signifies BLOCKED.

The dedicated Windows CI workflow generates A and B fixture stages, tests
non-overwrite behavior and malformed fixtures, and runs the **actual
Companion C# ForeverDbExportParser** against both generated versions.
This validates the fixture's format; it is not a successful user-Windows
GUI test.

## Safety and setup

Use Windows 10/11 x64 under the same Windows user that owns the local DPAPI state.
Preferred: Windows Sandbox or an isolated Windows user, **with test accounts and
their own disposable WoW SavedVariables**, not the historical production profile.
The launcher does **not** start Companion, authenticate, alter existing files,
change network connectivity or perform any API requests. It reads existing
Guildbook snapshot files and verifies the DPAPI envelope in memory; the report
contains no decrypted content, filenames, local paths, account IDs, tokens,
per-file checksums, or Guildbook names. The addon SavedVariables source is not
DPAPI-encrypted and remains outside the Companion store.

Download the `ForeverDB-Companion-win-x64` artifact **12551933942**
from run **40074802791**. Save the original ZIP at
`C:\ForeverDB-Test\ForeverDB-Companion-win-x64.zip` and extract to
`C:\ForeverDB-Test\app`. Do not execute inside ZIP. The launcher checks
the original artifact ZIP digest against
`109d5a768c33b47afdc4ced86b2c92783feafe94fec86009d6341cfef1d79ced`,
compares every extracted file to the ZIP, verifies file version 0.9.0,
and requires Windows CurrentUser DPAPI to work. This binds the executed
files to the pinned GitHub Actions artifact from the expected HEAD.

Run from the repository root in Windows PowerShell 5.1:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\guildbook-acceptance\Invoke-GuildbookAcceptance.ps1 -ArtifactZip 'C:\ForeverDB-Test\ForeverDB-Companion-win-x64.zip' -CompanionDirectory 'C:\ForeverDB-Test\app'
```

Run after verifying that the script came from this repository and that the
artifact downloaded from GitHub matches the pinned workflow. No admin rights
needed. Use `-NonInteractive` to produce BLOCKED for every manual
step. Use `-ReportDirectory` to choose a **new, private** report folder.
Do not point the report directory at existing ForeverDB/ WoW user folders.

## Interactive sequence

1. Verify a fresh registered test account A online, with Auto Sync OFF.
2. Make a new Guildbook capture with WoW, write SavedVariables using
   `/reload` or logout, and verify that A's roster appears.
3. Exit Companion via tray **Exit** (closing the window is not exit), restart,
   and verify the local roster returns without a new capture.
4. After verified online authentication, exit, disconnect network and restart.
   Verify the local roster is available. Reconnect afterward. A later
   server revocation is observed only on the next online verification.
5. Sign out; verify the private UI clears while encrypted file hashes remain
   identical. The script never reads Guildbook contents into its report.
6. Sign in as a separate registered test account B; verify A's guild is absent.
   Verify stale A capture cannot populate B (BLOCKED if not safe/possible to
   reproduce); create a **fresh** B capture and verify the second hashed
   account namespace appears without modification of A's files.
7. Sign out B, return to A and confirm A returns without exposing B.
8. Public observation sync and absence of Guildbook RPC require an **authorized,
   disposable private backend** and sanitized endpoint telemetry. The launcher
   neither invokes these calls nor packet-captures traffic. If not performed
   separately, mark BLOCKED. Do **not** use production for acceptance uploads.

Storage layout (hashed account and installation identifiers):
`%LOCALAPPDATA%ForeverDBguildbook<sha256-account><sha256-installation>snapshot.dat`
and optional `snapshot.dat.bak`.
A successful DPAPI probe proves CurrentUser decryption of the observed envelope,
not that the UI has displayed the correct contents. UI behavior is manually attested.
It is not possible to prove absence of an HTTP call from filesystem inspection alone.

## Report/exit semantics

File `guildbook-acceptance-YYYYMMDDTHHMMSSfffZ-random.json` is written
only in the chosen reports folder (never in Guildbook storage).

```json
{
  "schema": "guildbook-local-only-acceptance/v1",
  "mode": "REAL_WINDOWS_MANUAL_ACCEPTANCE",
  "timestamp_utc": "2026-10-26T10:00:00Z",
  "result": "BLOCKED",
  "source_head": "b47606061e21173ac091916e100cd51988d7ba90",
  "workflow_run": 40074802791,
  "artifact_id": 12551933942,
  "artifact_sha256": "109d5a768c33b47afdc4ced86b2c92783feafe94fec86009d6341cfef1d79ced",
  "checks": [
    {"id":"windows_dpapi","evidence":"AUTO","status":"PASS","code":"OK","required":true},
    {"id":"public_sync","evidence":"NOT_VERIFIED","status":"BLOCKED","code":"NOT_VERIFIED","required":true}
  ],
  "limits": ["Additional limitations are written here by the launcher"]
}
```

This is an illustrative format, **not a result from an actual Windows test**.
AUTO means filesystem/build/DPAPI check, MANUAL is a user attestation,
NOT_VERIFIED is BLOCKED. FAIL dominates BLOCKED; all required checks must PASS
for overall PASS. Exit codes: 0 PASS, 1 FAIL, 2 BLOCKED.
