## Mining live acceptance follow-up — 2026-11-11

The owner reported mining events 0→5, player-context-only 0→5, interaction-zone 0, source-map 0, duplicate source suppression working, and mining spell 2575 detected. This shows the event was recognized and at least one source GUID was available to the loot-window deduplicator. It does not prove that the same GUID was captured when the mining spell completed.

The mining spell handler stores only a `UnitGUID("npc")` that parses as a gameobject; otherwise its pending source GUID is nil. `GetPendingGatheringKind()` still permits a pending mining kind with a nil GUID, so the subsequent loot observation can be counted as mining. Geographic attribution is stricter: `resolveLootInteractionZone()` rejects the observation unless `pending.guid` is present and exactly equals the unique `GetLootSourceInfo()` GUID. It also requires the pending event-time map ID/name to match the valid, stable map identity at loot capture. Thus a loot GUID used for deduplication is not retroactive evidence that the earlier spell targeted that source. The strongest code-path explanation is the pending-source identity gate; without the local match result, a pending-map mismatch or invalid/transitioning map remains possible.

There is no source-coordinate API in this collector. `GetLootSourceInfo()` gives the loot source GUID; the map and normalized position APIs used by the collector are player-context APIs. They can support a zone-only interaction claim only with the event correlation checks above. Source-map remains zero and player coordinates must not be promoted to node coordinates.

Diagnostics terminology also matters: `player-context-only` is calculated as a subset of the persisted Unknown observations that have player location rows. For a new observation, global mining total increments once and either interaction-zone or Unknown increments once; a player-context-only count is a breakdown of Unknown, not an additional geographic class. Therefore a literal raw diagnostic output cannot show Unknown=0 and player-context-only=5 for this implementation. If the owner’s figures used those labels as mutually exclusive categories, no data inconsistency is implied. If the raw `/fdb geodiag` output showed that exact combination, capture its addon version and revision for a build/SavedVariables consistency check before changing the collector.

For zero-drop observations, an empty item set still counts as one source observation if the loot window can be tied to a known source GUID. It adds no item/drop/quantity counters. The test fixture verifies that a known fallback source is counted once as Unknown and repeated source GUIDs remain deduplicated. With no loot items and no readable source GUID, the collector records an unresolved window instead of inventing a mining source or observation.

No production attribution change is justified by the supplied aggregate evidence. The targeted regression fixtures cover a source GUID that appears only at loot time and zero-drop source counting. To isolate a future live sample, enable `/fdb debug` for one controlled mining interaction and privately check whether the pending spell message says a GUID was captured or `awaiting loot source`, then whether that pending GUID matches the unique loot-source GUID. Also keep the character in one zone for the sample and note whether the event-time zone stayed stable. Share only yes/no match and stability results; do not share GUIDs, names, coordinates, or SavedVariables.

## Safe repeatable gameplay acceptance

The addon diagnostic is read-only. It does not write SavedVariables, change revisions, reset counters, fork an installation, rebuild the export, or contact a network service.

The in-game command is `/fdb geodiag`. It prints the current persisted revision, `updatedAt`, SavedVariables schema, per-kind lifetime observation totals, and evidence counts (`unknown`, `interaction-zone`, `source-map`, `player-context-only`, `legacy/unclassified`, and `no-location-context`). It then reports whether `player`, `target`, `npc`, and `mouseover` have a recognized source-GUID type and candidate map ID, plus whether the world-cursor API exposes a readable gameobject GUID candidate. The probe never prints GUIDs, names, tooltip strings, or coordinates. Unit map IDs are candidate readings only, not source attribution.

1. Keep Companion closed for the entire sample. Ensure Auto Sync is off before the test and leave it off; do not open a Companion sync flow afterward until the owner has decided what to do with the test observations. The addon itself does not upload.
2. Log in to a test character on `wowf 1.60.1.70862`. Do **not** run `/fdb fork`, `/fdb session reset`, or any counter reset. Existing counters and SavedVariables are retained.
3. At the start of the sample, run `/fdb geodiag`. Save a screenshot or transcribe only the collector event counts, Unknown/context counts, API availability and revision. Do not share names, GUIDs, coordinates, or character/account identifiers.
4. Perform 20 controlled events for one collector class at a time: creature loot (`mob`), skinning, herbalism, mining, and ordinary fishing catches. Run `/fdb geodiag` after each 20-event group. Compare the start/end `events` line for that class; for fishing, record `fishing` and `fishing_pool` separately and report both. A smaller difference means some interactions did not produce a collector observation. Repeat the baseline/end pair for every class.
5. During a creature or skinning sample, run `/fdb geodiag` while the source target is still available. During herb/mining, run it while the node is targeted/hovered and immediately after the gather interaction. During fishing, run it while hovering the pool and after the catch. Record whether the candidate `target`/`npc`/`mouseover` unit map matches the player map and whether `world-cursor evidence` reports a readable gameobject GUID candidate. The command prints candidate map IDs only; those readings are probes, **not proof** that the event source has that map.
6. Include deliberate failure/ambiguity trials: move maps between interaction and result when safe, let gathering/fishing windows expire, use a missing or secret tooltip value if naturally available, and interact with a different source after an expired pending event. For creature-loot retest on Tirisfal, compare the `mob events`, `interaction-zone`, `unknown`, and `legacy/unclassified` deltas. `verified_interaction_zone` may increase only when the loot GUID is unique and the live API returns valid map metadata for the player's event-time map, with matching `GetZoneText`, stable before/after map identity, and a valid normalized map position. The command displays lifetime counters, so always compare start/end values. Existing global counters are not backfilled into Unknown or interaction-zone buckets; on older characters, `legacy/unclassified` can explain why global totals exceed the sum of current geographic buckets. Compare each value with its own baseline. The collector emits one geographic class for each newly recorded observation; if a fresh event changes a global bucket while Unknown and interaction-zone both stay unchanged, verify addon build and SavedVariables/revision identity before interpreting the report. Diagnostics do not create a disposable test bucket or provide an automatic “undo.”

## Geo A behavior

- Existing global source, item, and location counters remain intact for legacy compatibility.
- New `geographicStats.unknown` source/item counters aggregate every observation without a proven source map or verified loot interaction zone. They contain no coordinates or location rows.
- New `geographicStats.interactionZone` source/item counters record only the `(mapId, exact zone name)` of a unique `GetLootSourceInfo()` source captured by `LOOT_READY`, when `C_Map.GetMapInfo` confirms the same map ID/name and parent, the normalized player map position is valid, the zone name matches, and before/after map identity is stable. This is zone-only evidence; no player coordinates are copied into it or rendered as source markers. Pending gathering evidence also must be fresh, source-matched, and map-matched. A map ID alone, fallback target GUID, synthetic fishing source, absent/inconsistent map metadata, or multiple source GUIDs never qualifies.
- Export retains Companion header schema 9 and existing record types. Additive `Q|1|revision`, `Z|unknown|...`, and `Y|unknown|...` records carry revision and Unknown aggregates; the current Companion parser ignores unrecognized record types. No Companion or ingestion changes are part of Geo A.
- SavedVariables schema advances to 10. A schema-9 database receives empty Unknown and interaction-zone aggregates (no historical backfill) and revision 1.
- Every subsequent public snapshot mutation advances the persistent integer revision even when `updatedAt` remains in the same second. Export generation itself is read-only.
- A restored database with counters but no installation ID cannot silently receive a new identity or export those counters. Export is held until the user accepts `/fdb fork`; that action archives the old local SavedVariables and starts the new identity with zero active observations and cleared active Guildbook data. Existing server aggregates stay under the old identity; the fork uploads only new observations.
- Companion/server bootstrap comparison and server-side revision replay remain later-phase work; Geo A does not change ingestion behavior.
