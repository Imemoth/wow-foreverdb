## Review process

Three independent fresh-context reviews were performed during
implementation (none of the reviewers had written the code they reviewed):

- **Reviewer A** (after the lifecycle/XP/gold accounting engine, before any
  UI existed): found and the implementation fixed (1) a crash when a
  character's persisted `current.startedAt` (or another leaf field) was a
  wrong Lua type, which permanently wedged the tracker on every
  `PLAYER_ENTERING_WORLD` retry; and (2) a history-retention test that
  asserted only a count, which stayed green under a reversed-eviction
  mutation (evicting newest instead of oldest). Both were fixed with a
  reproduced-red-then-green regression test. Several coverage gaps (exact
  timeout/meaningful-session boundaries, the periodic checkpoint ticker,
  HUD-settings persistence) were also closed.
- **Reviewer B** (after the HUD, detailed window, and Core/TOC/CI wiring):
  found and the implementation fixed (1) the HUD's per-character saved
  position/visibility was applied once at `ADDON_LOADED`, before any
  character was active, and never re-applied once `SessionPlayerReady()`
  resolved the real character at `PLAYER_LOGIN`; and (2) `CreateFrame` was
  unconditionally asked for the `"BackdropTemplate"` virtual template,
  which errors on a client without `BackdropTemplateMixin` rather than
  degrading gracefully. Both were fixed and covered by tests that drive the
  real, unstubbed functions through the real `ADDON_LOADED` ->
  `PLAYER_LOGIN` order. Two non-blocking gaps (the StaticPopup
  reset-confirmation path was untested; the lock-toggle sequence was
  duplicated between the command and the button) were also closed.
- **Final whole-branch reviewer** (full diff from base main to branch head,
  after both prior reviews' fixes): re-verified independently that the
  XP/level-up reconciliation, timing/inactivity/offline/pause math, money
  exactly-once accounting, export-schema isolation, WoW API guard
  completeness, and UI/accounting separation all hold, and confirmed both
  prior reviewers' fixes are actually correct and still covered. Found and
  the implementation fixed one further blocking gap: `current.xp`/
  `current.gold` being well-formed *tables* with a wrong-typed *inner*
  leaf (e.g. `current.xp.gained` as a string) was not validated by the
  existing corrupted-state recovery, and crashed the tracker on the next
  accepted XP/money event, or during the archive-on-timeout check that
  can run at login. Reproduced both crashes directly against the
  production module before fixing, then covered with regression tests
  that corrupt only an inner leaf. Also strengthened a gold-rate test
  that could not distinguish active time from tracked time, and widened
  `isMaxLevel` to also cover a missing/non-numeric XP max per spec
  section 8.4.

## Review round 2 (external review against `44fbee1`)

An external code review examined the branch at `44fbee1` (the state after
the reviews above) and reported four further findings, all confirmed real
against the actual code and fixed with a reproduced-red-then-green
regression test per finding:

- **`de103da`** — BLOCKING: `SessionTracker.lua`'s own `PLAYER_ENTERING_WORLD`
  fallback (for a player GUID unavailable at `PLAYER_LOGIN`) called
  `SessionPlayerReady()` but nothing resynced the HUD's per-character saved
  position/visibility afterward, so a delayed GUID resolution left the HUD
  stuck at frame-build defaults indefinitely. Fixed by also registering
  `PLAYER_ENTERING_WORLD` on Core.lua's own frame and calling
  `SessionPlayerReady()` + `SyncSessionHUDForActiveCharacter()` there,
  both idempotent so a later ordinary `PLAYER_ENTERING_WORLD` (zone
  change, reload) starts no new session and creates no new frames/tickers.
- **`2306d5f`** — BLOCKING: `GetOrCreateSessionCharacter()` only checked a
  character record was truthy, not that it was a table, so a hand-edited
  SavedVariables value there (string/number/boolean) crashed the moment
  any field was written on it. Also, a history list mixing valid records
  with stray non-table entries crashed `GetSessionHistory()`'s copy loop
  the same way. Fixed with `type(char) ~= "table"` and a new
  `normalizeHistoryList()` that drops only the malformed entries while
  preserving every valid record and their order.
- **`e103241`** — BLOCKING: the periodic UI ticker only refreshed the
  compact HUD; an already-open detailed window's KPI/timing/character/
  rates/XP-bar values went stale until the next button click. Fixed by
  refreshing both views from the one registered ticker; verified the
  detailed window keeps refreshing even while the HUD itself is hidden.
- **`b2c94c9`** — BLOCKING: most widgets (HUD stat pairs, detailed-window
  KPI/Timing/Character/Rates fields, the XP bar, the history scroll
  viewport/content/rows, all five control buttons, the fallback
  reset-confirmation's text and buttons) were created but never actually
  positioned or sized — only the top-level panels and titles had a real
  `SetPoint`/`SetSize`. The mocks were strengthened first (SetPoint became
  cumulative and recorded per-anchor instead of silently discarded; SetSize
  now actually stores width/height) so "no real anchor" is directly
  observable, then every widget was laid out for real, including history
  rows each getting a distinct vertical position and the scroll content
  child's height tracking the actual row count so 30 records genuinely
  overflow a fixed-height viewport.
- **`7a755b8`** (minor, not separately blocking) — Started and history
  Date/Time displayed a raw UNIX epoch number; added `formatTimestamp()`
  with a safe "--" fallback, verified with a test that fails under a
  reverted-to-`tostring()` mutation.

**Reviewer C** (fresh, independent, had not written any of review round
2's fixes) reviewed the branch at `0c48024` against this project's fixed
10-point round-2 checklist, ran the full verification suite itself
(confirmed the 50/38/8 counts, compiles, and scope claims made above at
that point in time), and confirmed by direct execution against the
production modules that `de103da`, `e103241`, and the character-record
half of `2306d5f` hold up exactly as claimed, with 4 of the round's
regression tests independently confirmed to reproduce red pre-fix. It
also found two further blocking issues and one test-quality gap, all
confirmed real and fixed in `c578530`:

- **Mid-session history corruption still crashed the archive write
  site.** `2306d5f`'s `normalizeHistoryList()` fix only covered the two
  *read* sites (`GetOrCreateSessionCharacter`, `GetSessionHistory`), not
  `ArchiveCurrentSessionIfMeaningful`'s `char.history = char.history or
  {}` write. Corruption introduced mid-session (after login's own
  normalization already ran) still crashed `table.insert`. Fixed by
  normalizing at the write site too.
- **Recent Sessions rendered oldest-first, not newest-first** —
  contradicting `b2c94c9`'s own comment and normal UX expectations.
  `char.history`'s append/evict order (oldest-appended-first) is correctly
  load-bearing for eviction and was left unchanged; the display now reads
  from the reversed position so the most recent session always renders at
  row 1.
- **Test quality**: `hasAnchor()` would have passed a degenerate
  `obj:SetPoint()` call with no arguments at all — it proved a call
  happened, not that it anchored anywhere real. Strengthened to require a
  real point/relativeTo/relativePoint, verified against both a degenerate
  and a real call. Reviewer C was explicit that this gap did not mask any
  currently-live bug (every actual `SetPoint` call site already passes
  real arguments) — it closes a residual weakness against future
  regressions.

Reviewer C also flagged, as non-blocking: a `.historyScroll.width`
table-field read that only ever worked because of the mock (fixed
alongside the ordering bug, replaced with the real `GetWidth()` API); and
a discrepancy it could not resolve between "4 blocking findings" recorded
here and "6 numbered findings" mentioned in its own task brief for the
original external review, since that review's original text is not
stored in this repository. Reviewer C explicitly stated it did not have
the approved mockup image available and so could not perform any visual
comparison against it — noted here rather than silently omitted.

## Live Forever acceptance — PENDING

**Nothing below may be marked PASS from mocks, Lua tests, compilation, or
CI alone.** It requires a real Forever client session with visual
confirmation and observed XP/gold/time behavior. Each item is unchecked
until a person records real-client evidence (screenshot, combat log
comparison, or explicit confirmation) against it.

### HUD

- [ ] Appears correctly with the approved dark/gold-bronze presentation.
- [ ] Can be dragged while unlocked.
- [ ] Lock prevents dragging.
- [ ] Hide/show works.
- [ ] Position survives `/reload`.
- [ ] Values refresh live (approximately every second).
- [ ] RUNNING / IDLE / PAUSED transitions are visually correct.

### Detailed window

- [ ] `/fdb session` opens/closes it.
- [ ] KPI row matches live state (XP/hr, XP gained, To level, Gold
      earned/spent, Net gold).
- [ ] XP progress bar updates as XP is gained.
- [ ] Recent Sessions history scrolls and shows prior sessions.
- [ ] Pause/Resume buttons work and reflect status.
- [ ] Reset requires confirmation (button and `/fdb session reset`) and
      starts a new session only after confirming.
- [ ] Positive/negative net gold formatting (green/red) is correct.

### Accounting flow

- [ ] A kill or quest turn-in that grants XP increases XP gained.
- [ ] Loot or another positive money event increases gold earned.
- [ ] A repair or purchase (negative money event) increases gold spent.
- [ ] A level-up leaves XP gained correct across the level wrap (no
      double-count, no lost XP).
- [ ] `/reload` continues the same session (tracked/active time do not
      reset; offline/reload gap is excluded from tracked/active time).
- [ ] A short relog (well within the configured offline timeout) continues
      the same session.
- [ ] Being offline longer than the configured offline timeout starts a
      new session on the next login, and the prior session appears in
      Recent Sessions if it was meaningful.
- [ ] 5+ minutes (or the configured inactivity timeout) without XP or
      money activity stops active time from growing further.
- [ ] The first XP/money activity after an idle period resumes active-time
      accounting (without backfilling the idle gap).
